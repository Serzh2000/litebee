# Шаги миссии LiteBee Go: как приложение упаковывает moveXYZ, circle, circleAlt и остальные

Документ — результат чтения кода установленного LiteBee Go. Дрон не трогали, сетевых портов не открывали.
Эталонные упаковщики с самотестом: `step_packers.py` в корне проекта (`python -X utf8 step_packers.py`).

## 0. Что проверено вживую, а что нет

**Вживую проверены только cmd 0, 1, 2, 3, 5, 50** (calibrate, takeOff, autoLand, moveXY, moveZ, RGB).
Всё остальное в этом документе — то, что приложение *положило бы* в кадр. Это не гарантия, что прошивка дрона
разбирает кадр так же. Для moveXYZ (10), circle (12), circleAlt (13) прошивка пока не проверялась.

Уровни уверенности в таблицах:

| Метка | Смысл |
|---|---|
| **КОД** | однозначно следует из кода приложения (GUI + main-процесс): именно эти байты приложение отправит |
| **КОД+SIM** | то же, и независимо подтверждено декодером в 3D-симуляторе вендора (`Assembly-CSharp.dll`), который читает те же 12 байт |
| **ВЫВОД** | не следует прямо из кода, это моё толкование |
| **НЕИЗВЕСТНО** | в коде приложения нет |

## 1. Источники

1. **GUI** — `gui/lib.min.js`, расширения `litebeeWingFormation` (то, что использует пользователь) и
   `litebeeStars` (другая линейка, но те же cmd). Блок → массив `[id сообщения, ...байты]`, который уходит в main-процесс.
2. **main-процесс** — `app.asar`, обработчик `handle(e)` и класс с `appendCmdAndTime`. Превращает массив в `(cmd, время, 12 байт)`
   и отправляет кадры при `formation_sendMission`.
3. **3D-симулятор** — `resources/formation/3D/Unity_C06_Primer_Data/Managed/Assembly-CSharp.dll`. Его приложение запускает кнопкой
   «демо». Класс `FormationUtility` разбирает те же `cmdSequence/dataSequence/timeSequence` (приложение пишет их в
   `Documents/unity3d.json`). Я дизассемблировал IL через reflection (скрипт `il_dump.ps1` в scratchpad) и перенёс декодер в
   `sim_decode()` в `step_packers.py`. Это единственный независимый «читатель» байтов, который у нас есть.

Что симулятор НЕ даёт: он ничего не знает про прошивку. Для speed/yaw/local360/flip/jump/atti он вообще не читает данные
(классы `SpeedData`, `YawData`, `Local360Data`, `RollData`, `BounceData`, `AttitudeData` без полей).

## 2. Общая схема

### 2.1. Путь данных

```
Scratch-блок --(GUI: _16To8, массив e)--> main handle(e) --(appendCmdAndTime)--> кадры при sendMission
```

* GUI `_16To8` — это `Int16Array` → байты, **little endian, знаковые** (значения >32767 переходят в отрицательные, дробные
  усекаются к нулю). Положительные сантиметры до 32767 эквивалентны `<H`.
* main `arr8ToU16([lo, hi])` — `Uint16Array`, little endian. `arr16To8` — то же в обратную сторону.
* Позиция клетки `_transPos(cell) = [40*parseInt(cell/12), (cell%12)*40]` = **[row_cm, col_cm]**. Первое поле — строка (ось y коврика),
  второе — столбец (ось x). Для moveXY это проверено вживую.
* Время в GUI: `Math.floor(10*секунды)`, то есть тики по 0,1 с (floor, не round: у проекта `ticks()` использует round,
  различие только для значений вроде 2,35 с).

### 2.2. Кадр шага (уже проверен для проверенных cmd)

`[19,0,3,2, total,0,index,0, t_lo,t_hi, cmd, 12 байт данных]`. `t` — **накопленное время конца шага** с начала программы дрона
(тики по 0,1 с, u16 LE). `appendCmdAndTime(дрон, cmd, dt, data12)` делает `timeTotal += dt`, и в шаг идёт новое `timeTotal`.
Контрольная сумма дрона — сумма байтов cmd всех шагов.

### 2.3. «Внешние» шаги (RGB, int) идут отдельным списком

RGB-блоки не двигают часы программы. Приложение складывает их в отдельный список `ext*`, ставит им время
`часы_в_момент_блока - 3` (если часы > 8, иначе 0) и **при отправке дописывает в конец** после всех шагов движения; нумерация
`index` продолжается. `total` в каждом кадре = число шагов движения + число RGB-шагов. Проект кладёт RGB по месту, а не в конец, и со
временем `now` без сдвига. Для cmd 50 это работает вживую, так что расхождение, судя по всему, безвредно (**ВЫВОД**).

## 4. moveXYZ (cmd 10) — блок «move to QR code [CODE], meanwhile fly to the height [Z], execute for [TIME] seconds»

В `show.py` это `code_z(cell, z, seconds)`.

| Поле | Значение |
|---|---|
| Аргументы блока | `CODE` — номер клетки, `Z` — высота в см, `TIME` — секунды |
| Сообщение GUI | `[153, T_lo, T_hi, row_lo, row_hi, col_lo, col_hi, z_lo, z_hi]`, значения `_16To8([T, row, col, z])`, `T=floor(10*TIME)` |
| Время шага (добавка к часам) | `T` (u16 из e1,e2) |
| Данные (12 байт) | `[0-1] i16 row_cm`, `[2-3] i16 col_cm`, `[4-5] i16 z_cm`, `[6-11] нули` |
| Эндианность | little endian |
| Z | **абсолютная** целевая высота, не прибавка (симулятор: цель `(col, z, row)`, интерполяция из текущей точки; шоу чередуют 80/130, это согласуется) |
| Деление на подшаги | нет, один шаг; в отличие от moveN/square ничего не делится |
| Фрагмент кода main | данные = `[e3,e4,e5,e6,e7,e8,0,0,0,0,0,0]`, время из `arr8ToU16([e1,e2])` |
| Фрагмент кода симулятора | `GetMove3DData`: три `ToInt16` со смещений 0, 2, 4; x=col, y=высота, z=row, масштаб 0,01 |
| Уверенность | раскладка и время: **КОД+SIM**. Что прошивка читает так же: **НЕИЗВЕСТНО**, но порядок row, col совпадает с проверенным moveXY, а высота лежит там же (смещение 4), где у соседних шагов нули |

Симулятор двигает дрон из текущей точки в целевую по прямой, равномерно за всё время шага (все три оси одновременно).

Связанные варианты:

* `litebeeStars.moveXYZ(X, Y, Z, TIME)` шлёт `_16To8([T, Y, X, Z])`, то есть `row_cm = Y`, `col_cm = X`. Это подтверждает порядок «сначала строка».
* `formation_notCode_XYZ` (157): время `10*e1` (секунды целым числом, не `Math.floor(10*TIME)`), данные `[e2..e7]+нули`. Ни один блок
  установленного GUI его не шлёт, смысл 6 байт — **ВЫВОД**, те же три i16.

## 5. circle (cmd 12) — блок «[cw/ccw] circle [COUNT] semicycle, take (point between [CODE1] and [CODE2]) as the centre point, execute for [TIME] seconds»

В `show.py`: `circle(count, cell1, cell2, seconds, rotate)`.

| Поле | Значение |
|---|---|
| Аргументы блока | `ROTATE` (cw → 0, ccw → 1), `COUNT` — число **полуоборотов**, `CODE1`, `CODE2`, `TIME` — секунды |
| Центр | `floor(0,5 * (a + b))` по каждой оси от `_transPos` двух клеток: `[row_cm, col_cm]`, целые сантиметры |
| Сообщение GUI | `[154, dir, count, T_lo, T_hi, row_lo, row_hi, col_lo, col_hi]`, `T = floor(10*TIME)` |
| Данные (12 байт) | `[0-1] i16 centre_row_cm`, `[2-3] i16 centre_col_cm`, `[4-5] u16 T`, `[6] count`, `[7] 0`, `[8] dir`, `[9-11] нули` |
| Эндианность | little endian для 16-битных полей |
| Фрагмент кода main | данные `[e5,e6,e7,e8,e3,e4,e2,0,e1,0,0,0]`, время `arr8ToU16([e3,e4]) * e2` |
| Фрагмент кода симулятора | `GetAroundData`: центр с 0 и 2, `ToInt16` со смещения 6 → число полуоборотов, `data[8]==0` → по часовой |
| Уверенность | раскладка и время: **КОД+SIM**. Что прошивка читает так же: **НЕИЗВЕСТНО** |

### 5.1. Время circle — самое важное

Шаг добавляет к часам **`T * count`**, где `T = floor(10*TIME)`. То есть **`TIME` в блоке — длительность ОДНОГО полуоборота**,
а весь шаг длится `COUNT × TIME`. В данных (байты 4-5) лежит именно `T` — период одного полуоборота. (**КОД**; симулятор тоже
крутит `count*180°` равномерно за всё время шага, то есть те же `TIME` на полуоборот.) Официальная справка называет
`p5` просто «время выполнения», что можно прочитать и как общее; код однозначен.

Следствие для проекта: `Drone.circle(..., seconds)` в `show.py` считает `seconds` общим временем шага. По приложению шаг
длится `count * seconds`. Для шоу это даёт (длительности по модели проекта → по модели приложения):

| Шоу | Дрон | проект | приложение |
|---|---|---|---|
| my_dream | 1, 2, 4–10 | 154,5–163,5 с | 177,5–186,5 с (+23 с) |
| my_dream | 3 | 167,5 с | 180,5 с (+13 с) |
| my_people_my_country_5 | 4, 8, 9, 10 | 183 с | 197 с (+14 с) |
| my_people_my_country_5 | 1, 2, 3, 5, 6, 7 | 185/169 с | без изменений (только circle с count=1 или без circle) |

Какую модель имели в виду авторы шоу, по самим шоу однозначно не решается. Косвенный довод за «TIME на полуоборот»:
линейная скорость по окружности π·r/TIME получается ≤ 69 см/с (при радиусе до 221 см), как и у обычных ходов
(медиана 40 см/с), а при «TIME на весь шаг» была бы до 139 см/с. Для воспроизведения поведения LiteBee Go
нужна модель приложения: в миссию кладётся `T*count`.

### 5.2. Геометрия по симулятору (**ВЫВОД** для прошивки)

* Центр круга — заданная точка `(col, row)` в текущей высоте дрона.
* Радиус = расстояние от **текущей позиции дрона в начале шага** до центра. Дрон должен быть на нужном расстоянии до шага.
  Если шагу предшествует `code` на эту клетку, радиус определяется ею. В шоу радиусы 85–221 см (my_dream) и 85–160 см
  (my_people_my_country_5), нулевых нет. `circle(2, 66, 66, ...)` — центр совпадает с клеткой 66, радиус берётся от дрона до этой клетки.
* Угол = `±180° × count`, знак зависит от `dir` (0 = по часовой в смысле симулятора). Равномерно за время шага. Два полуоборота возвращают
  дрон в начальную точку.
* Высота при circle не меняется (байты 4-5 `T` симулятор не читает, использует свою текущую высоту).
* В системе симулятора x = столбец, z = строка. «По часовой» у вендора считается при взгляде сверху; как это ложится на
  направление строк реального коврика, из кода не следует.

## 6. circleAlt (cmd 13) — блок «[cw/ccw] circle a semicycle, take (point between [CODE1] and [CODE2]) as the centre point, meanwhile fly to the height [Z], execute for [TIME] seconds»

В `show.py`: `circle_z(cell1, cell2, dz, seconds, rotate)` (в шоу не используется).

| Поле | Значение |
|---|---|
| Аргументы блока | `ROTATE`, `CODE1`, `CODE2`, `Z` — см, `TIME` — секунды |
| Сообщение GUI | `[155, dir, T_lo, T_hi, row_lo, row_hi, col_lo, col_hi, z_lo, z_hi]`, `T = floor(10*TIME)`, центр как в circle |
| Данные (12 байт) | `[0-1] i16 centre_row_cm`, `[2-3] i16 centre_col_cm`, `[4-5] u16 T`, `[6-7] i16 z_cm`, `[8] dir`, `[9-11] нули` |
| Время шага | `T` — **ровно один полуоборот** за весь шаг (счётчика полуоборотов у блока нет) |
| Фрагмент кода main | данные `[e4,e5,e6,e7,e2,e3,e8,e9,e1,0,0,0]`, время `arr8ToU16([e2,e3])` |
| Фрагмент кода симулятора | `GetAroundHData`: высота `ToInt16` с 6 → абсолютная цель (`height - текущая высота`), `data[8]==0` → по часовой |
| Уверенность | раскладка и время: **КОД+SIM**. Абсолютность Z: **КОД+SIM** (английский текст блока «fly to the height»; китайская справка говорит «поднимается на»; `show.py` называет аргумент `dz` и считает прибавкой, **это расходится с симулятором**) |

Связанные варианты:

* `formation_circle_XYZ` (158) даёт cmd 13 с временем `e1` (сырые тики, не ×10), `ue = u16(e1)` в байтах 4-5, данные
  `[e3,e4,e5,e6,ue0,ue1,e7,e8,e2,0,0,0]`. Блоков нет, смысл полей — **ВЫВОД**.
* `litebeeStars.circleXY / circleXYZ` шлют центр как `(Y, X)` → `row = Y`, `col = X`. Подтверждает порядок.
* cmd 14 (`AroundD`) известен только симулятору: раскладка cmd 13 плюс `i16 degree` в байтах 9-10 (дуга произвольного угла).
  Приложение его не создаёт. Есть ли он в прошивке, неизвестно. Не использовать.

## 8. RGB и int (cmd 50 / 51)

Время RGB-шагов — ext-схема из п. 2.3, не часы движения.

| Вариант | Откуда | cmd | Данные (12 байт) | Время | Уверенность |
|---|---|---|---|---|---|
| Wing `RGB` / `RGBValue` (GUI всегда шлёт `[165, 1, r, g, b]`) | `formation_RGB_value`, e1 == 1 | 50 | `[5,0,2,255,g,r,b,0,0,0,0,0]` (порядок **g, r, b**) | `часы-3`, если часы > 8, иначе 0 | **вживую** (раскладка в `mission.rgb_data`) |
| Индекс цвета 0–7 | GUI: бит0 = R, бит1 = G, бит2 = B → 255 | то же | то же | то же | вживую |
| `RGB_N` (164) | main, блоков нет | 50 | `[10,0,3,r,g,b,255,255,255,255,255,255]` (порядок **r, g, b**) | `часы-3` | **КОД**, НЕ проверено |
| Stars `RGB`/`RGBValue` (шлёт `[165, 0, r, g, b]`) | `RGB_value`, e1 != 1 | 50, но 51 если `sendMission` с флагом 1 | как RGB_N | `часы-3` | **КОД**, НЕ проверено |
| `formation_RGB` (156) с 254/255 | скрытые тест-блоки | 50 | `[5,0,2,2,128,33,46 или 47,0...]` | `часы-5` | **КОД**, НЕ проверено |

Cmd 51 (`int`): `sendMission` с флагом 1 заменяет cmd *всех* ext-шагов с 50 на 51. Это делает только расширение Stars. Wing
шлёт флаг без значения, ext-шаги остаются cmd 50.

## 9. speed (4), yaw (6), flip (8), jump (9), atti (11)

Id перечислены в `cmd`, но **ни GUI, ни main-процесс таких шагов не строят**, а симулятор разбирает их как шаги без данных
(`SpeedData`, `YawData`, `RollData`, `BounceData`, `AttitudeData` — пустые классы). Раскладку 12 байт вывести нельзя.
Упаковщики `pack_speed/yaw/flip/jump/atti` в `step_packers.py` честно бросают `NotImplementedError`.
Источники, которые могли бы помочь: документация прошивки Litebee/Wing (не найдена), перехват трафика другого клиента.

используются ни `code_s`, ни `circle_z`, ни `rgb_value`, ни `local360`.

| my_people_my_country_5 | `(1, 89, 89, 8, cw)` | 12 | (280, 200) | `18 01 c8 00 50 00 01 00 00 00 00 00` | 80 |
| my_people_my_country_5 | `(2, 66, 77, 7, cw)` | 4 | (220, 220) | `dc 00 dc 00 46 00 02 00 00 00 00 00` | 140 |

Время шага — по модели приложения (`T*count`, см. 5.1). Радиусы от предыдущей клетки до центра: 85–221 см (my_dream),

## 11. Предлагаемый минимальный живой тест (один дрон)

Правила для всех тестов: один дрон, на коврике, с зафиксированной позицией (`position_problem`), высота взлёта 100 см,
защитные кольца на винтах, рука на аварийной посадке (`LAND_NOW`, `all_autoLand`). Сначала загрузка без `--go`: контрольная сумма
подтверждает, что прошивка приняла id шагов (по сумме cmd), но не раскладку.

**Принцип границы риска**: все числа в пакете взяты небольшими (≤ 130), стартовая клетка выбрана рядом с началом координат
коврика. Тогда любая неверная трактовка полей даёт цель не дальше `max(поле)` от начала координат, а ошибка по позиции
не превышает расстояния от старта до начала коврика (113 см для клетки 26).
Нулевые байты тоже могут быть прочитаны как координата 0, поэтому оценка включает угол коврика (0, 0).

### 11.1. Тест A1 — moveXYZ только по вертикали (старт: клетка 26 = row 80, col 80)

| № | Шаг | cmd | t_end (тики) | Данные |
|---|---|---|---|---|
| 1 | calibrate 5 с | 0 | 50 | нули |
| 2 | takeOff 100 см, 5 с | 1 | 100 | `64 00` + нули |
| 3 | moveXYZ клетка 26, z=130, 3 с | 10 | 130 | `50 00 50 00 82 00 00 00 00 00 00 00` |
| 4 | moveXYZ клетка 26, z=100, 3 с | 10 | 160 | `50 00 50 00 64 00 00 00 00 00 00 00` |
| 5 | autoLand | 2 | 160 | нули |

Контрольная сумма = 23. Ожидание: подъём на 30 см и спуск обратно на месте.
Если раскладка неверна, пакет содержит числа {80, 80, 130, 0}:

* по горизонтали дрон может пойти в точку (130, 80), (80, 130) или в угол коврика (0, 0): худший случай **≈ 113 см** от старта (в угол);
* по высоте цель может оказаться 0 (посадка со скоростью ~33 см/с), 80 или 130. Выше 130 см не поднимется.

### 11.2. Тест A2 — moveXYZ с горизонтальным сдвигом на 40 см

Шаги 3 и 4: `moveXYZ клетка 27, z=120, 4 с` (`50 00 78 00 78 00 ...`, t_end 140) и `moveXYZ клетка 26, z=100, 4 с`
(`50 00 50 00 64 00 ...`, t_end 180). Ожидание: сдвиг на +1 столбец (+40 см по x) с подъёмом до 120 см и возврат. Если строка и
столбец поменяются местами, дрон сдвинется на +40 см по строке вместо столбца, это хорошо видно. Худший случай (числа пакета
{80, 120, 120, 0}) такой же, как в A1: **≈ 113 см** (угол коврика), по высоте не выше 120 см.

### 11.3. Тест C1 — circle, полуоборот (центр = клетка 27, старт клетка 26)

Центр (row 80, col 120), радиус 40 см, `count=1`, `TIME=6` с, `cw`.

| № | Шаг | cmd | t_end | Данные |
|---|---|---|---|---|
| 1–2 | calibrate, takeOff 100 | 0, 1 | 50, 100 | как выше |
| 3 | circle, count=1, TIME=6 | 12 | 160 | `50 00 78 00 3c 00 01 00 00 00 00 00` |
| 4 | moveXY обратно на клетку 26, 4 с | 3 | 200 | `50 00 50 00` + нули |
| 5 | autoLand | 2 | 200 | нули |

Контрольная сумма = 18. Ожидание по симулятору: дрон идёт по полуокружности радиуса 40 см вокруг (80, 120), заканчивает в
(80, 160), дуга выгибается в сторону больших строк (через клетку 39); потом возвращается. Если выгнулось в другую сторону,
это только направление `cw`, не ошибка раскладки.

Худший случай, если раскладку прочитали неправильно: центр может оказаться в любой точке с координатами из {0, 1, 60, 80, 120}, радиус
до **113 см** (центр в углу (0,0)), полуоборот переносит дрон на противоположную точку этой окружности, то есть до **≈ 226 см** от
старта, за пределы коврика в отрицательную сторону. Правдоподобные ошибки порядка (строка/столбец) дают зеркальный круг
того же радиуса 40 см, безвредный.

### 11.4. Тест C2 — circle, полный оборот против часовой

Шаг 3: `circle count=2, TIME=4, ccw` → cmd 12, t_end 180, данные `50 00 78 00 28 00 02 00 01 00 00 00`; потом autoLand (t_end 180).
Контрольная сумма 15. Проверяет, что общий шаг идёт `count × TIME` = 8 с, что число полуоборотов читается из байта 6 и что
`dir=1` даёт обратное направление. Дрон должен вернуться в стартовую точку. Худший случай как в C1.

Рекомендуемый порядок: A1 → A2 → C1 → C2; следующий тест только после чистого результата предыдущего.

## 12. Итог

### Определённо (по коду приложения)

* Формат: GUI → main → кадр; все 16-битные поля little endian, GUI знаковый; время — накопленное, 0,1 с, floor.
* moveXYZ (10): `[i16 row, i16 col, i16 z, 6 нулей]`, время `floor(10*TIME)`, z абсолютная.
* circle (12): `[i16 центр row, i16 центр col, u16 T, count, 0, dir, 0,0,0]`, **время шага = T*count**, TIME на один полуоборот.
* circleAlt (13): `[i16 центр row, i16 центр col, u16 T, i16 z, dir, 0,0,0]`, один полуоборот за T.
* local360 (7): `[dir, нули]`, время `floor(10*TIME)`.
* RGB: Wing-раскладка `[5,0,2,255,g,r,b,...]` (cmd 50, проверено), прочие варианты и cmd 51 описаны выше.
* Эти же раскладки независимо читает симулятор вендора.

### Выведено

* Что прошивка читает моддвижения так же, как симулятор (центр + радиус от текущей позиции, прямая линия для moveXYZ).
* Смысл `cw` на реальном коврике, смысл local360, смысл 158/157.

### Открытые вопросы

1. Прошивка не проверялась для cmd 10, 12, 13: раскладка подтверждена только кодом приложения и симулятором.
2. Использует ли прошивка байты 4-5 (`T`) circle или считает скорость вращения из `t_end` шага. В пакетах приложения оба согласованы
   (`t_end` = `T*count`), так что любое чтение даёт то же.
3. Направление `cw` на коврике; радиус берётся от фактической позиции дрона, не плановой (ошибка позиции ±10–15 см меняет радиус).
4. Модель времени circle в `show.py` (`seconds` — общее) расходится с приложением (`TIME` на полуоборот); нужно решить, какую хранить в DSL.
5. `circle_z` в проекте трактует `dz` как прибавку; приложение и симулятор — как абсолютную высоту.
6. Раскладки speed (4), yaw (6), flip (8), jump (9), atti (11) в приложении отсутствуют вовсе.
7. RGB в приложении идёт в конец списка и на 0,3 с раньше; проект ставит RGB по месту (для cmd 50 это работает вживую).
8. Верхние границы: время шага u16 (до 6553,5 с), `count` ≤ 255 (один байт), координаты ≤ 32767 для знакового чтения.
