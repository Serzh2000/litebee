# LiteBee Go: камера, зрение, режимы «метки / линия / цвет / ИИ» и обновление дрона

> **Поправка (2026-11-06, по мобильному приложению):** вывод ниже о том, что кадры «группы 2» принадлежат только C10, неполон. Мобильное приложение Wing тоже шлёт кадры группы 2 по UDP на `192.168.100.1:9696`, но в виде команд подгруппы 3 (значения 20–27). Подгруппы 12–14 (скорость, высота, поворот) строит библиотека C10. См. [WING_MOBILE_APP.md](WING_MOBILE_APP.md).


Разбор установленного приложения LiteBee Go (Electron, версия 40.9.3), только чтение кода. Ничего не запускали, в сеть не ходили, дроны не трогали.

Разобранные файлы:
* `resources\gui\lib.min.js` (16 МБ, расширения Scratch «flight», канал `flightChannel`, `AIBlocks`);
* `resources\app.asar` распакован в `main.js` (одна строка 180 КБ) и `preload.js`;
* `resources\apriltag_wasm.wasm`, `resources\cache\drone_info.json`, `resources\cache\melis30_1.5.elf`, `resources\gui\AI_module`, `resources\ocr`;
* прошивка `melis30_1.5.elf` читалась через DWARF (скрипты `tools/firmware/`) только для сверки названий.

Метки достоверности у каждого утверждения:
* **ПРОЧТЕНО** — видно в коде (указаны функция/константа и смещение в байтах в файле);
* **ВЫВОД** — наше заключение из прочитанного;
* **НЕИЗВЕСТНО** — из этих файлов не узнать.

Смещения: `lib` = `lib.min.js`, `main` = `main.js` (байты от начала файла, «около»).

## 0. Главное

1. **Два разных семейства устройств, и камера у них устроена по-разному.**

| | LiteBee Wing (расширения `litebeeWing*`) | LiteBee Bot / C10 (расширения `litebeeBot`, `litebeeBotML5`) |
|---|---|---|
| Канал команд | USB-пульт, serial 115200: `FD FD len` + сообщение `[id, …]` | Wi-Fi `192.168.5.1`: TCP 17788, кадр `FA` + `[len,0,item,subitem,данные]` + CRC-16 |
| Канал ответов | пакет пульта `FC FC … 0E` (30 байт) | UDP 17789, кадры `FA len 01 01 item данные FB` без CRC |
| Видео | отдельный модуль камеры C06, Wi-Fi `192.168.100.1`, RTSP | RTSP `192.168.5.1:8554/ch0` и `/ch1` |
| Прошивка из приложения | нет (приложение Wing не обновляет) | да: `c10_drone_firmware`, файл `melis30_<версия>.elf` |

   ПРОЧТЕНО: `handleDeviceSend` и `DeviceConnectService` (`main` ~38300, ~64000): списки устройств `REMOTE_DEVICES`, `LITEBEE_BOT_DEVICES`, `NO_HANDSHAKE_DEVICES`.

2. **Поправка к `docs/PROTOCOL_SINGLE.md`, раздел «Живые команды: кадры группы 2».** Кадры вида `[len,0,2,id,…]` (взлёт `[9,0,2,3,3,…]`, режим `[10,0,2,11,6,режим,…]` и т.д.) строит не «новый класс расширений Wing», а класс **`litebeeBot`** (и `litebeeBotML5`): ПРОЧТЕНО, `lib` 9473979–9517714, `EXTENSION_ID` = `litebeeBot` на 9501144, `litebeeBotML5` на 9517714. Отправляются они по TCP 17788 на `192.168.5.1`, а не через USB-пульт (`flight:send` в `main` ~162751: для `litebeeBot` вызывается `tcp.sendData`; `sendData` добавляет `FA` и CRC-16, `main` ~14346). Расширения настоящего Wing (`litebeeWing`, `litebeeWingLine`, `litebeeWingCode`, `litebeeWingClamping`, …) используют старые сообщения `[id,…]` (`vel_control` 27, `mode_control` 29, `pos_control` 30, `passthrough` 26, `line_control` 28). Группа 2 — это раздел `control` протокола awlink (ВЫВОД, см. 1.3).

3. **Файл `melis30_1.5.elf` — прошивка семейства Bot/C10 (V853S + E907), а не Wing.** ВЫВОД, опора: имя облачного пакета `c10_drone_firmware`, путь на дроне `/mnt/bakup/melis30.elf`, адреса `192.168.5.1`, камера «C10» в `AIBlocks.setC10Camera`; сам Wing-пульт и камера C06 обновляются иначе (в приложении кода для этого нет).

4. **Распознавание AprilTag на ПК не связано с бортовым.** Кнопки «recognize apriltag in image» работают на кадре, который приложение берёт из видео, детектор — WASM в процессе Electron, tag36h11 (см. раздел 3). Бортовые «метки» читает камера дрона сама и отдаёт `id`, смещения (раздел 2).

### 1.3 Bot (C10): кадры группы 2 (то, что мы раньше приписали Wing)

Кадр: `FA` + `[len, 0, item, subitem, данные…]` + CRC-16 (таблица из `main` модуль «11», MCRF4XX: init 0xFFFF, отражённый 0x8408, байты результата младший-старший; сверено с `litebee/protocol.py`). `len` = число байт данных после четырёх байт заголовка (проверка: `[9,0,2,3,3,0×8]` = 9 байт данных). Поля заголовка в терминах прошивки `awlink_recv_s` (магик, `length`, `id_src`, `item_id`, `subitem_id`, данные, 2 байта CRC): `len`, `0` = `id_src`, `2` = `item_id` (control), следующий = `subitem_id`. ВЫВОД (форма совпала с DWARF структурой).

* Отправка по Wi-Fi: `sendData` в очереди из не более 3 кадров, не чаще раза в 50 мс; если за 200 мс не пришли новые данные и номер миссии не изменился, тот же кадр дублируется по UDP (ПРОЧТЕНО, `main` ~14346 и конструктор класса tcp). ВЫВОД: дублирование как слабая защита от потерь.
* Все построители `setDir`/`setYaw`/`setHigh` те же, что в `litebee/live.py` (проверено сравнением).

## 2. Как приложение читает ответ дрона

### 2.1 Wing: пакет пульта `0E`

Транспорт: USB-пульт (CP210x `10C4:EA60` или CH340 `1A86:7523`, 115200). Кадр от пульта `FC FC len data…`, тип в `data[0]`: `0xE9` приветствие, `0x0D` версия (`FV`, `RV`), `0x0E` пакет данных (`main` ~9146, функция `remoteDataHandle` класса remote). Пульс: байт `00` каждые 500 мс, обрыв после трёх тактов тишины (ПРОЧТЕНО; совпадает с `PROTOCOL_SINGLE.md`).

Разбор данных в `remoteDataHandle(e,t)` (`main` ~49574; `e` — данные после байта `0x0E`, 30 байт; `t` — строка версии `"(FV1.2.3,RV1.1.1)"`):

| Байты `e` | Поле | Разбор |
|---|---|---|
| 0–5 | `pos.x`, `pos.y`, `pos.z` | три int16 LE, как есть (см) |
| 6–11 | `roll`, `pitch`, `yaw` | три int16 LE × 0,1° (`toFixed(1)`) |
| 12 | `vol` | байт × 0,1 В |
| 15 | `mode` | режим полёта (таблица: 0 самост., 1 определ. высота, 2 определ. точка, 3 взлёт, 4 посадка, 5 следование, 6 миссия, 7 круг, 8 переворот, 10 стоп, 11 360, 12 прыжок, 13 линия) |
| 16–18 | `vel.x/y/z` | три int8 |
| 19–28 | блок модуля расширения | зависит от версии, см. ниже |
| 29 | `mission` | номер миссии |

Блок модуля (`e[19…28]`): версия FV превращается в число `i = FV[0]+FV[1]+FV[2]` (строка «123», сравнивается как число):

| Условие | Разбор (ПРОЧТЕНО, `main` ~50514–52400) |
|---|---|
| `e[19] != 255` и `i < 109` (FV ниже 1.0.9) | старая раскладка без номера модуля: `e[19]=line.type`, `e[20]=color`, `e[21]=theta` (int8), `e[22]=rho` (int8), `e[23]=cross`, `e[24]=crossX` (int8), `e[25]=crossY` (int8) |
| `i ≥ 109`, `e[19]==1` | линия + метка: `type=e[20]`, `color=e[21]`, `theta=e[22]`s, `rho=e[23]`s, `cross=e[24]`, `crossX=e[25]`s, `crossY=e[26]`s; метка: если `e[27]==1`, то `code.id=e[28]` (один байт), иначе −1 |
| `e[19]==2` | метка + ИИ: если `e[22]==1`, то `code.id = e[20] + (e[21]<<8)`, иначе −1; `ai.total=e[23]`, `ai.id=e[24]`, `ai.label=e[25]` |
| `e[19]==3` | цвет: `color=e[20]`; если `i>126` (FV ≥ 1.2.7), то `colorCount[0..3]=e[21..24]` |
| `e[19]==5` | ИИ-вариант: `ai.id=−1`; если `e[20]==1`: `ai.id=e[21]`, `ai.label=e[22]`; если `e[20]==2`: `ai.id=0`, `ai.label=256·e[21]+e[22]` |
| `e[19]==16 / 17` | сторонние данные `thirdData[0..8]` или `[9..17]` из `e[20..28]` |
| `e[19]==255` | ToF: бит `e[20]` (1,2,4,8,16) включает значение: `t1=e[21]`, `t2=e[22]`, `t3=e[23]`, `t4=e[24]`, `t5=e[25]`, иначе 0 |

Выводы:
* ПРОЧТЕНО: **единицы и масштабы** не преобразуются; `theta`, `rho`, `cross*` — int8 без масштаба, `id` метки 8 или 16 бит; для линии «направление» кодируется маской 1 = назад, 2 = влево, 4 = вперёд, 8 = вправо (по таблицам в `recvDataHandle`, `lib` 11875102).
* ВЫВОД: байты блока при `e[19]==1` совпадают с началом структуры прошивки `cameraData_s` (+1 `line_type`, +2 `line_color`, +3 `line_theta` int8, +4 `line_rho` int8, +5 `line_cross`, +6 `line_cross_x` int8, +7 `line_cross_y` int8): то есть пульт/дрон передаёт эти поля почти как есть. Байт `e[19]` ближе к «`func` / типу блока», чем к самому `func` (значения 1, 2, 3, 5, 16, 17, 255 не совпадают с `CAMERA_FUNC_*` 1…4, поэтому прямой связи не утверждаем).
* НЕИЗВЕСТНО: как дрон/пульт составляет эти 10 байт из `cameraData_s` (40 байт), значения `e[19]` для режима «метки» без линии (в коде метка приходит вместе с линией при `1`, и с ИИ при `2`).
* НЕИЗВЕСТНО: в Wing-пакете нет x, y, z, angle метки (`cameraData_s.x/y/z/angle`), только `id`; позиция берётся из `pos` (то есть оценивается бортом).

**Как запрашивается режим на Wing (ПРОЧТЕНО):** сообщением `[26,1,m,…,2]` (m: 0 метки, 1 линия, 2 цвет, 3 ИИ) и последующим `[29,…]` (см. 1.2). Какой модуль сейчас активен, приложение узнаёт по `e[19]` в каждом пакете (ВЫВОД: поле «текущий модуль»; соответствие `m` ↔ `e[19]` не доказано).

**Версии в Wing:** FV дрона и RV пульта приложение выводит строкой `(FVx.y.z,RVa.b.c)` (`main` ~9146, `remoteDataHandle` за 0D). Сравнение с минимальной версией нет, версия лишь выбирает раскладку (пороги 1.0.9 и 1.2.7). ПРОЧТЕНО.

### 2.2 Bot: статусный поток UDP 17789

Приложение отправляет байт `00` в UDP при открытии и затем каждые 200 мс; пропуск 15 тактов (≈3 с) = обрыв (ПРОЧТЕНО, `main` ~28265+, класс udp). Дрон шлёт кадры:

`FA, len (<128), 01, 01, item (<11), данные[len], FB`

Контрольной суммы нет (кадр принимается, если после данных стоит `FB`). Последовательность: байт 2 = 1 (`id_src`), байт 3 = 1 (`item` status), байт 4 = `subitem` (в коде «item»). ВЫВОД по сходству с `awlink_recv_s`.

Subitem 0 (40 байт данных, int16 LE, смещения в байтах):

| Байты | Поле |
|---|---|
| 0–1 | высота по барометру /100 |
| 2–3 | давление |
| 4–5 | температура /10 |
| 6–11 | ускорение xyz /100 |
| 12–17 | гироскоп xyz /100 |
| 18–23 | roll, pitch, yaw, каждый /10 (градусы) |
| 24–25 | дальномер (`rangefinder`, используется как высота) |
| 26–29 | `vel[0]`, `vel[1]` |
| 30 | напряжение ×0,1 В |
| 31 | версия: значение − 1 |
| 32 | режим полёта |
| 33 | флаг программирования |
| 34 | RSSI (0 = нет связи) |
| 35 | номер миссии |
| 36–39 | `pos[0]`, `pos[1]` (int16) |

Subitem 3 (**камера**, ПРОЧТЕНО, `main` ~28265–31300): запись в `sensorData`:

| Байт данных | Поле приложения | Смысл |
|---|---|---|
| 0 | `cameraIR` | биты 0…3 = ИК вправо, влево, назад, вперёд |
| 1 | `cameraMode` | текущий режим камеры, 1 линия, 2 метки, 3 цвет, 4 ИИ |
| 2 | `cameraFlag` | достоверность (результат есть) |
| 3–19 | `cameraData[0..16]` | 17 байт данных режима |

Разбор `cameraData` в расширении Bot:

| Режим | Разбор |
|---|---|
| 1 линия | `cameraData[2]`: бит 1 = назад, 2 = влево, 4 = вперёд, 8 = вправо |
| 2 метки | `Int16Array(cameraData[0..9])` = пять int16: `[0]` `id`, `[1]` смещение «Y» (`getCodeDeltaCenterY`), `[2]` смещение «X» (`getCodeDeltaCenterX`), `[3]` и `[4]` приложением не читаются |
| 4 ИИ | `cameraData[3]` = число объектов; i-й объект: `X = cameraData[4+2i]`, `Y = cameraData[5+2i]`, байты со знаком (подпись блока: «tank») |

ВЫВОД: пять int16 метки соответствуют короткому формату кадра позиционного модуля из `FIRMWARE_MARKERS.md` (разд. 3): `id`, два смещения, расстояние, курс; следовательно `[3]` = расстояние и `[4]` = курс ×0,1°. Не проверено на дроне.

Subitem 6: `thirdData` (сторонние алгоритмы), без разбора на стороне приложения кроме вывода: `thirdData[0]` идентификатор алгоритма (16, 17 цвет; 18, 19, 23, 24 прочие; 20 карточки; 21 лицо и маска; 22 20 классов объектов), `thirdData[1..8]` четыре пары `256·hi+lo` = `x, y, w, h`, `thirdData[9]` метка (таблицы названий в `lib` ~9495597), `thirdData[10..17]` спектр F1…F8. ПРОЧТЕНО.

### 2.3 Поле `func` прошивки и структура `cameraData_s`

ПРОЧТЕНО (DWARF `melis30_1.5.elf`): `cameraData_s` (40 байт): `+0 func, +1 line_type, +2 line_color, +3 line_theta(i8), +4 line_rho(i8), +5 line_cross, +6 line_cross_x(i8), +7 line_cross_y(i8), +8…+11 line_width*, +12 line_flag, +13 line_id, +14 id(i16), +16 x(i16), +18 y(i16), +20 z(i16), +22 angle(i16), +24 flag, +25…+32 c1x…c4y, +33 aid, +34 threshold, +35 prob, +36 ax, +37 ay, +38 aw, +39 ah`. ### 2.4 Бортовые метки в приложении: формулы

В классе канала (`lib` ~11860000) положение относительно метки считается из `pos`, а не из камеры: ПРОЧТЕНО (`getCodeDeltaCenterX/Y`): ряд метки = `floor(id/12)`, столбец = `id%12`, шаг 40 см, наборы A {108…110,120…122,132…134} с целью (x=50, y=5) и B {111…113,123…125,135…137} с целью (x=50, y=20). Совпадает с прошивкой (`FIRMWARE_MARKERS.md` разд. 4, 8).

### 3.2 Цепочка «блок → результат»

1. Блок `apriltagRec` → `AIBlocks.apriltagImgRec()` (`lib` 11891148). Если предыдущий запрос ещё идёт (`apriltagRecFlag`), новый пропускается.
2. Рендерер берёт `canvas.toDataURL("image/jpeg")` (качество по умолчанию 0,92) и вызывает `electronAPI.imgHandle({type:"apriltag_rec", data})`. ВЫВОД: перед этим на canvas уже применён «image zoom factor» (`apriltagScale` ≥ 1: цифровое увеличение с обрезкой при отрисовке, `lib` ~11895800).
3. Главный процесс: `ipcMain.handle("img-handle")` → при `type` с префиксом `apriltag` вызывается `handleImgHandle` (`main` ~165000), а из него `ApriltagService.detectFromBase64` (`main` ~104528–108600). Тот же сервис обрабатывает `apriltag_local` (диалог выбора jpg/png) и `apriltag_save` (сохранение в `Downloads\img_00..02.jpg`).
4. Предобработка (ПРОЧТЕНО, `_detectFromBufferAsync`): `nativeImage.createFromBuffer`, при ширине > 1280 уменьшение до 1280 (высота пропорционально); `toBitmap()` (BGRA), серый = среднее `(b+g+r)/3`, округлённое.
5. WASM: `atagjs_init`, затем `atagjs_set_detector_options(2,0,1,1,0,1,1)`, `atagjs_set_img_buffer(w,h,stride=w)`, `atagjs_detect()`; результат — указатель на JSON-строку со списком детекций (`corners` — четыре точки `{x,y}`, `center`, `pose.t[]` и т. д.). ПРОЧТЕНО (`main` ~107000–108900). Расшифровка семи параметров детектора (decimate = 2,0; sigma = 0; потоков 1; refine_edges = 1; max_detections 0; return_pose 1; return_solutions 1) — ВЫВОД по известному интерфейсу AprilTag JS (в самом wasm не проверяли).
6. Берётся **только первая детекция** (`g[0]`); `id` метки в результат не попадает.

Семейство: в WASM только `tag36h11` (в строках файла других семейств нет). ПРОЧТЕНО.

### 3.4 Прочие функции ПК-зрения

* OCR и сопоставление картинок: процесс `resources\ocr\ocr.exe` (Python, OpenCV, torch), запускается из `main` (`cnocrPath`, `main` ~36141). Протокол через stdin/stdout: приветствие «OK»; строка `0<каталог>\match\n` — инициализация; `1<путь к jpg>\n` — сопоставление (ответ JSON `{code:2,img,score}`); `2<путь>\n` — OCR (`{code:0,data}`). * ИИ в браузере (блоки Bot-ML5, лица, поза, KNN): `ml5` + `p5`, модели в `gui\AI_module` (BlazeFace, FaceMesh, BlazePose, MobileNet, faceapi), работают на видео, дрону ничего не шлют. ПРОЧТЕНО.
* Интерфейс веб-сервера: WebSocket `ws://localhost:48712` (`WsServer` в `main`) для внешнего клиента: сообщения `connect`, `disconnect`, `poll` (отдаёт `{ext, data}` из кэша), остальное пересылается в `app_handle`. ПРОЧТЕНО (`main` ~5000+). ВЫВОД: этим можно читать то же, что видит рендерер (без USB-пульта в нашем коде), но здесь не проверялось.

### 4.3 Протокол загрузки (Bot по Wi-Fi)

Порты `192.168.5.1`: TCP **17788** (команды и ответы), TCP **17880** (данные файла), UDP 17789 (статус), WebSocket 8266 (MicroPython REPL). ПРОЧТЕНО (`main` ~4000–5440).

Последовательность `drone_update` (`main` ~40000–41000, ~86000–94000):

| Шаг | Что происходит | Формат |
|---|---|---|
| 1 | `getFileMetadata`: считается MD5 файла (потоком) и размер | |
| 2 | Команда «принять файл» по TCP 17788 | `FA` + `[100,0,6,0]` + 80 байт пути (`/mnt/bakup/melis30.elf`, добивка нулями) + размер uint32 LE + 16 байт MD5 (бинарный) + CRC-16 (та же функция, что у всех кадров) |
| 3 | Ответ дрона (TCP 17788) | `FA 01 01 06 02 <статус> FB`; **статус 0 = готов** (приложение смотрит через 100 мс; `getUploadStatus` читает и сбрасывает) |
| 4 | Если статус 0, открывается второе TCP-соединение на 17880 | |
| 5 | Файл передаётся порциями до 4096 байт | без заголовка, без CRC |
| 6 | После каждой порции дрон на 17880 присылает uint32 LE «сколько осталось»; приложение ждёт значение `общий размер − отправлено` (опрос каждые 100 мс, до 1 с, до 3 повторов порции; при неуспехе «Failed to send total … after 3 retries») | подтверждение количеством |
| 7 | По завершении приложение отправляет в TCP 17788 кадр `FA 00 00 06 01 78 46`, то есть `[0,0,6,1]` без данных + CRC, закрывает 17880 и через 1 с сбрасывает статус | команда item 6, subitem 1 |

Уверенность: шаги ПРОЧТЕНО (`droneUpdater.getFileMetadata`, `sendFile`, `updateDroneFirmware`, `tcp.on_data`); значения «item 6 = файловая группа», «subitem 1 = применить/перезагрузить» — ВЫВОД (по контексту; в прошивке есть `big_kernel_ota_handle(uint8_t*,len)`, ПРОЧТЕНО по имени). Что дрон делает дальше (перепрошивает E907 из `/mnt/bakup/`, перезагружается): ВЫВОД.

Тот же механизм использует отправка программ Python (`sendFile` в tcp-классе, путь `/root/aa`, MD5 из нулей, порт 17880, код оборачивается в `_thread.start_new_thread`) и настройка точки доступа (`/mnt/my_hostapd.conf`, параметры SSID, пароль, диапазон 2.4G канал 6 или 5G канал 149). ПРОЧТЕНО.

Контрольные суммы: CRC-16 на командных кадрах (MCRF4XX, ПРОЧТЕНО, совпадает с `litebee/protocol.py`); MD5 всего файла в метаданных; на самих порциях только подтверждение количеством. В статусных кадрах (UDP) CRC нет. ПРОЧТЕНО.

Замечание о надёжности (ВЫВОД): между шагами 2 и 3 стоит фиксированная задержка 100 мс (а MD5 считается асинхронно перед отправкой), поэтому статус «готов» легко пропустить: если ответа ещё нет (`−1`), обновление молча не начинается.

## 6. Что это значит для нашего проекта

1. Если цель — читать камеру Wing, источник один: байты 19–28 пакета `0E` пульта (раздел 2.1), которые в `docs/PROTOCOL_SINGLE.md` значатся как «модули расширения, не расшифровано»; их можно расшифровать по таблице раздела 2.1 и сверить на живом дроне в режимах «линия», «метки», «цвет», «ИИ» (запросы режима: `[26,1,m,0×7,2]` и `[29,2,…]`; сначала проверить на дроне без пропеллеров, что пульт пропускает сообщения `passthrough`: этого мы не проверяли).

3. Для сравнения «бортовое против ПК» можно запускать WASM AprilTag отдельно (`apriltag_wasm.wasm`, tag36h11) и повторить формулы из 3.3.
