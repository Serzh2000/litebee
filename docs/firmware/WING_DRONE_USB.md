# Дрон Wing по USB (ADB): что снято с живого устройства

Снято 2026-11-06. Дрон подключён к компьютеру по USB, при питании от аккумулятора, без пропеллеров. Только чтение: файлы скопированы, разделы флеша прочитаны через временный файл в `/tmp` (оперативная память), на флеш ничего не записывалось. Пометки: **ПРОЧТЕНО**, **ВЫВОД**, **НЕИЗВЕСТНО**.

## 1. Доступ (ПРОЧТЕНО)

* Дрон отзывается по ADB: `18D1:0002`, серийный номер `20080411` (стандартный номер Allwinner, совпадает с серийным номером модуля с камерой, различать устройства по нему нельзя).
* Подключение сработало после питания от аккумулятора; от одного USB дрон не поднимался (ADB показывал `offline`; ВЫВОД: не хватало питания).
* Старый `adbd` не поддерживает `exec-out`; файлы забираются через `adb pull`, разделы флеша через `cat /dev/mtdblockN > /tmp/...` и `pull`.
* Оболочка BusyBox без `id`, `which`, `head`, `strings`.

## 2. Что за система (ПРОЧТЕНО)

* `Linux sun8i 3.4.39-rt143 #19 PREEMPT RT Tue Mar 21 09:49:00 CST 2023`, ARMv7, Allwinner A33.
* Флеш (NOR/NAND, 8 разделов): `uboot` 256 КБ, `boot` 1320 КБ, `rootfs` 2416 КБ, `env` 128 КБ, `Netprivate` 128 КБ, `recoveryk` 1320 КБ, `recoveryf` 2416 КБ, `recoverye` 128 КБ. Корень смонтирован как `squashfs` (только чтение), `/netPrivate` как vfat. Побитовые копии всех восьми разделов сняты (папка `06_wing_drone_flash_raw`).
* Работают: `init`, `flow`, `/img_app/pilot/pilot_f` (то есть автопилот **`pilot_f`**, а не `pilot`), `wpa_supplicant -iwlan0` и `udhcpc -iwlan0` (дрон в режиме **клиента Wi-Fi**: файл `/netPrivate/wifiActor` содержит `WifiActor=CLIENT`), `adbd`, `pmonitor`, `sunxi_poweroff_detection`, `getty` на консоли 115200. `VideoTransmission` не запущен.

## 5a. Живая проверка приёма (ПРОЧТЕНО, 2026-11-06)

* Из памяти работающего `pilot_f` прочитано: номер канала `int_dev0` = 0 (`ttyS0`), длина данных по умолчанию = `0x14` (20), что подтверждает, что приёмник ждёт кадр с 20 байтами данных (`CD` + 20 + сумма). Чтение памяти проверено на известной строке (`[%s]use int_dev0`).
* Буфер приёма `int_dev0` (структура по адресу `0x70a30`, данные с `0x70a3b`) **пуст**: ни одного принятого кадра.
* Счётчики драйвера UART: `/dev/ttyS0` **tx: 831 байт, rx: 0**; `ttyS2` и `ttyS1` без обмена. Значит, дрон передаёт в `ttyS0` (команды модулю), но **ничего не принимает**: модуль не отвечал. Причина: **модуль в этот момент был отключён от дрона** (подтвердил владелец, модуль подключался к компьютеру отдельно). Повторить с подключённым модулем. У `pilot_f` открыты: `/dev/ttyS0`, `/dev/ttyS2`, `/dev/icm_imu`, `/dev/STM8s`, `/dev/dps280`, лог `/tmp/log.bin`.

## 5b. Приём с подключённым модулем (ПРОЧТЕНО, 2026-11-06)

Модуль подключён к дрону, дрон по USB с аккумулятором, пропеллеры сняты.
* Счётчик UART: `/dev/ttyS0` **rx 20152 -> 20262** за несколько секунд (110 байт = 5 кадров по 22 байта), tx 360. Дрон принимает кадры модуля.
* Буфер приёма `int_dev0` в `pilot_f` (по адресу `0x70a3b`, 20 байт данных) содержит: `02 00 00 ff c6 ff d9 01 78 00 1a 00 00 00 00 00 00 00 00 00`. Это байты 1–20 кадра модуля без заголовка `CD` и без суммы: тип `02`, `id` = 0, смещения `ffc6` (−58) и `ffd9` (−39), расстояние `0178` (376), угол `001a` (26), **флаг = 0** (метки в кадре нет, поля показывают последние значения). Счётчик принятых данных в структуре состояния равен `0x14` (20).
* Вывод: цепочка модуль -> `ttyS0` -> приёмник `int_dev0` -> буфер `pilot_f` работает с кадром, который снят в памяти модуля (`POSITION_MODULE_V831.md`, раздел 3), раскладка данных совпадает байт в байт.

## 5c. Метка 0 под камерой (ПРОЧТЕНО, 2026-11-06)

Модуль над меткой 0, дрон принимает. Данные в буфере `pilot_f`: `02 00 00 ff fc 00 16 01 28 0d f3 01 00 00 00 00 00 1f 01 00`:
тип 2, `id` 0, x = `fffc` (−4), y = `0016` (22), расстояние `0128` (296), угол `0df3` (3571), **флаг 1** (метка найдена), ToF = `011f` (287 мм, байты 17–18, младший первым). Следующие кадры: угол 3570, ToF 286.
* Расстояние метки (296) близко к ToF (287 мм): единицы расстояния миллиметры. Угол 3571 рядом с 3600: единицы 0,1° (357,1°, почти нулевой поворот). x и y (−4 и 22), по всей видимости, тоже миллиметры (ВЫВОД: модуль над центром метки).
* Журнал `/tmp/log.bin` (21 КБ) на неполётном дроне содержит только записи `SYS` и `MSG` и таблицу форматов; записей `APRIL` нет, они пишутся, судя по всему, только в полёте. Формат записи `APRIL` по таблице: `hfffHB`.
* **Формула положения найдена в `pilot_f` дрона** (дизассемблер, функция около `0x1efb0`, сокращённая версия `0x1e9c0`) и совпадает с формулой образа 1.2.8: структура метки `[id u16][+2 x][+4 y][+6 расстояние][+8 угол]`; константы в `.data` по адресу `0x51200`: шаг **40,0**, масштаб **8,333**, коэффициент высоты **10,2**, общий множитель 0,01. `id / 12` даёт строку, `id % 12` столбец. Первая выходная ось = (`y` × 0,01 × 8,333 + строка × 40) × 0,01; вторая = (`x` × 0,01 × 8,333 + столбец × 40) × 0,01; высота = расстояние × 10,2 × (малый коэффициент, около 1e-4). Угол приводится к ±180.
* Расчёт по живому кадру метки 0 (`x` = −4, `y` = 22, расстояние 296): первая ось ≈ +0,018 м, вторая ≈ −0,003 м, высота ≈ 0,30 м (ToF 287 мм). Значит единицы `x` и `y`: 1 ед. ≈ 0,83 мм, расстояние ≈ 1,02 мм на единицу. Живое значение положения из памяти дрона не снималось (расчёт по формуле).

## 5d. Два режима Wi-Fi, два автопилота (ПРОЧТЕНО, 2026-11-06, вторая загрузка)

Файл `/netPrivate/wifiActor` на дроне поменял значение между двумя подключениями: сначала `WifiActor=CLIENT`, потом `WifiActor=SERVER`. Список процессов разный:

| Режим | Wi-Fi | Автопилот | Прочее |
|---|---|---|---|
| `CLIENT` | `wpa_supplicant`, `udhcpc` (дрон подключается к сети) | `pilot_f` | `flow` |
| `SERVER` | `hostapd` (дрон сам раздаёт сеть), `udhcpd` | **`pilot`** | `flow`, `VideoTransmission` (камера и видео), **`ftpd`** (FTP-сервер) |

**Причина переключения (со слов владельца): дрон унёсли из помещения с нужной Wi-Fi сетью.** Значит, `CLIENT` включается, когда сеть доступна, а без неё дрон переходит в `SERVER` (сам раздаёт сеть) и запускает другой автопилот (ВЫВОД, механизм выбора не разобран). Связь режима и автопилота выведена из двух наблюдений. `/img_app/run.sh` запускает только `VideoTransmission`; кто выбирает `pilot` или `pilot_f`, не выяснено (НЕИЗВЕСТНО).
* В режиме `SERVER` приёмник модуля в `pilot` находится по другому адресу (структура состояния `0x71a38`, данные с `0x71a43`). Чтение этого буфера дало данные, не похожие на кадры метки (первый байт растёт 0x3d, 0x3e, потом `14 02 00 0d 00`), а указатель на разобранную метку оказался нулевым: приёмник `pilot` в этом режиме я не разобрал. Счётчик `rx` у `ttyS0` растёт (110 байт за несколько секунд), то есть модуль на связи (НЕИЗВЕСТНО, что именно лежит в буфере).
* Кадр, прочитанный в режиме `CLIENT` на `pilot_f` (раздел 5c), остаётся единственным подтверждённым чтением приёма.
* **Дополнение по статическому разбору `pilot`.** Приёмник в `pilot` (функция `0x34c44`) имеет ту же логику, что `pilot_f` (одинаковые начальные значения: канал 0 = `ttyS0`, длина кадра по умолчанию 20). Отличаются только адреса данных (состояние `0x71a38`, данные с `0x71a43`). В прочитанном буфере на смещении 16 лежат байты `02 00 0d` (тип 2, номер 13: под камерой в этот момент была метка 13), то есть кадр метки приходил, но записан не с начала области данных. Почему (счётчик `ip` в состоянии не сбрасывается при ошибке суммы, поэтому после сбоя запись идёт дальше по буферу), статически не выяснено. ВЫВОД, не проверено; нужен живой разбор при загруженном `pilot_f` и `pilot`.
