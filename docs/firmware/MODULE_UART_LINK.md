# UART-связь `pilot` Wing с внешними модулями (камера положения, дальномер)

Источник: `img_app/pilot/pilot` из `Wing_V1.2.8 FM_V1.1.2.img` (ARM, без символов, адреса виртуальные, база 0x10000), чтение дизассемблера. Нужно, чтобы понять, как позиционный модуль передаёт дрону `id` маркера и что должна выдавать подставная камера.
Пометки: **ПРОЧТЕНО** (в коде), **ВЫВОД**, **НЕИЗВЕСТНО**. Ничего не проверено на живом дроне.

## 1. Порты и скорость (ПРОЧТЕНО)

* Автопилот открывает `/dev/ttyS0` и `/dev/ttyS2` (`pilot 0x37690..0x37724`, флаги `O_RDWR|O_NOCTTY|O_NONBLOCK`, `0x902`) и читает по 64 байта (`0x37804`, `0x377b0`).
* Скорость задаёт функция `0x37744`: для 57600 берётся константа `B57600` (0x1001), во всех остальных случаях **`B115200` (0x1002)**; при открытии порта вызывается с 0x1002. Вывод: по умолчанию **115200, 8N1** (формат 8N1 прямо в коде не проверялся).
* Какой порт какой модуль обслуживает (ttyS0 или ttyS2), по коду не определено (НЕИЗВЕСТНО).

## 2. Кадры к модулю (передача) (ПРОЧТЕНО)

Две почти одинаковые функции (`0x34efc` для «ext device uart», `0x36928` для канала `int_dev0`) собирают кадр:
`0xAD, 0xFA, данные[n], sum8`, где `sum8` = сумма байтов данных по модулю 256. Длина передачи n + 3. У второй функции длина данных берётся из байта 9 структуры минус 0x64.
Что именно отправляется (команды выбора режима камеры и т. п.), не разобрано.

## 3. Кадры от модуля `int_dev0` (приём) (ПРОЧТЕНО, функция `0x369ac`)

Конечный автомат принимает байты и собирает кадр с двухбайтовым заголовком из значений `0xCC`, `0xCD`, `0xCE`:

| Заголовок | Длина данных | Примечание |
|---|---|---|
| `CC CC` | 14 байт | в структуре ставится признак `0x78238[0] = 1` |
| `CD CD` | 20 байт | |
| `CE CE` | 5 байт | |

Затем идёт один байт контрольной суммы `sum8` (сумма байтов данных). При совпадении данные (до 20 байт) копируются вызывающему (`memcpy` из `0x78243`). Код проверяет второй заголовочный байт независимо от первого, то есть формально допускает смешанные пары (ВЫВОД: на практике это дублированные байты, как у `AD FA`).
В этом обработчике видна фильтрация расстояния (деление на константу, порог, счётчик подряд идущих значений), то есть эти кадры, по крайней мере частично, относятся к **дальномеру или модулю потока**, а не к маркерам (ВЫВОД).

## 4. Приём «ext device uart» (ПРОЧТЕНО, функция `0x2fea8`)

Читает до 10 байт за раз (`0x3400c` выбирает драйвер по флагу устройства). Автомат: ждёт `0xFA`, затем второй `0xFA`, затем байт (запоминается как длина или тип) и накапливает сумму. Разбор дальше (`0x2fc9c`) не прочитан (НЕИЗВЕСТНО).

## 5. Где сидит разбор кадра маркера (ПРОЧТЕНО, функции 0x1fb24, 0x33f8c, 0x344c0)

Цепочка вызовов установлена по дизассемблеру:
1. Функция `0x1fb24` (раз в цикл) просит кадр через `0x33f8c(…, buf=0x7eedb, 0x11)`.
2. `0x33f8c` смотрит байт `0x78160+0x0d`. Если он не нулевой, управление уходит в приёмник `int_dev0` (`0x369ac`, раздел 3). Если нулевой, возвращается 0. **Приёмник «ext device uart» (раздел 4) в этот буфер не пишет.**
3. `0x1fb24` выбирает тип сообщения: если признак версии `0x78238[0]` ≠ 0 (то есть уже был принят кадр `CC CC`), тип принудительно равен 2; иначе тип берётся из первого байта буфера.
4. Тип 2 вызывает `0x344c0`, **единственный** вызов разбора маркера (`0x1ff0c`). Остальные типы (ПРОЧТЕНО): 1, 4, 5 копируют несколько байт в служебные структуры, 0xF9 ставит флаг.

Итог по формату тела (поля int16, старший байт первым):

| Режим | Откуда | Раскладка |
|---|---|---|
| `0x78238[0]` ≠ 0 (кадр `CC CC`, 14 байт) | `id` 0–1, смещение 2–3, смещение 4–5, расстояние 6–7, курс 8–9, флаг 10 (остаток 11–13 здесь не читается) | прочитано |
| `0x78238[0]` = 0 (кадр `CD CD`, 20 байт) | байт 0 тип (=2 для маркера), `id` 1–2, смещения 3–4 и 5–6, расстояние 7–8, курс 9–10, флаг 11, ещё поле 12–13 | прочитано |

Кадр `CE CE` (5 байт) обрабатывается отдельно (разные пары байт, похоже на смещения потока), маркеров в нём нет (ВЫВОД).
Признак `0x78238[0]` ставится при первом `CC`-кадре и в просмотренной ветке не сбрасывается (ВЫВОД: после первого `CC CC` типы из байта 0 больше не используются, пока модуль не перезапущен).

## 5a. Следствие для подставной камеры (ВЫВОД, на железе не проверено)

Самый простой кадр, который `pilot` примет как маркер, это `CC CC` + 14 байт тела + `sum8`:

```
CC CC | id_hi id_lo | dx_hi dx_lo | dy_hi dy_lo | dz_hi dz_lo | yaw_hi yaw_lo | flag | 00 00 00 | sum8
```

* `sum8` = сумма 14 байт тела по модулю 256 (в приёмнике сравнивается именно с накопленной суммой данных, заголовок не входит).
* `flag` = 1: маркер виден; 0: `id` заменяется на −1.
* Расстояние должно быть больше 100, `id` меньше 288 (проверки из `FIRMWARE_MARKERS.md` раздел 4), курс в десятых долях градуса.
* Если такой кадр на железе вызовет движение, значит любое семейство маркеров можно выдать за AprilTag, просто подставив `id`. Предупреждение: перед проверкой снять пропеллеры.

## 6. Что проверить логическим анализатором (практический шаг)

Теперь известно, что искать на линии между модулем и дроном:
1. Скорость 115200 (или 57600), 8N1.
2. Кадры, начинающиеся с `CC CC`, `CD CD`, `CE CE` (от модуля) и `AD FA` (к модулю).
3. Последний байт кадра = сумма байтов данных по модулю 256.
4. Кадр с маркером: тело 11 или 14 байт; `id` в первых двух байтах (обратный порядок байт не определён), три смещения int16, курс, флаг.
Если захват подтвердит заголовки и длины, подставная камера на любом семействе маркеров сможет слать такие кадры.

## 7. Что осталось

* Какой из портов (`ttyS0` или `ttyS2`) является `int_dev0`, и включается ли `int_dev0` по флагу конфигурации (в логе есть строка `use int_dev0`, байт `0x541ec`).
* Содержимое типов 1, 4, 5, 0xF9 и кадра `CE CE`.
* Что отправляется модулю командой `AD FA …`.
* Единицы смещений (сантиметры или иные), проверка формулы на живом дроне.
