# Как прошивка LiteBee исполняет миссию и режимы управления

Источник: `melis30_1.5.elf` (RISC-V E907, Melis, база 0x47c00000, версия 1.5 «тестовая»). Только чтение и дизассемблирование, ничего не запускалось.
Модули: `flight/app/app_mission.c`, `app_control_mission.c`, `app_control_circle.c`, `app_control_takeoff.c`, `app_control_land.c`, `app_control_jump.c`,
`app_control_local360.c`, `app_control_poshold.c`, `app_control_common_pos.c`, `app_control_track_lines.c`, `app_failsafe.c`, `app_control.c`.
Связанные документы: [PROTOCOL_STEPS.md](../PROTOCOL_STEPS.md) (как приложение пакует шаги), [FIRMWARE_ARCHITECTURE.md](../FIRMWARE_ARCHITECTURE.md), [FIRMWARE_MARKERS.md](../FIRMWARE_MARKERS.md).

Метки уверенности: **ПРОЧТЕНО** (видно в коде, указаны адрес и функция), **ВЫВОД** (следует из прочитанного, но не видно напрямую), **НЕИЗВЕСТНО**.
Все адреса в виде `0x47c...`. Единицы: `data[i]` это `int16` (little endian) в массиве `mission_node_s.data[6]`; байты кадра `b0..b11` = `data[0]` (b0,b1), `data[1]` (b2,b3) и т.д.

## 0. Главные выводы (коротко)

1. Тип шага (`type`, он же `cmd` в кадре) разбирает таблица переходов из 21 записи в `mission_process_task` (0x47c4989e, таблица 0x47c5a85c). Номера 0..14 совпадают с `cmd` из PROTOCOL_STEPS.md; типы 15..19 пустые, 20 равен 0, 50 и 51 это «ext» (отдельный механизм).
2. Раскладки шагов, подтверждённые прошивкой: takeOff (`u16` z, см), moveXY (`row_cm`, `col_cm`), moveZ, moveXYZ (`row`, `col`, `z`), circle (центр, T, число полуоборотов, направление), circleAlt (центр, T, z, направление). Всё совпадает с PROTOCOL_STEPS.md, кроме мелочей из раздела 8.
3. Новое по сравнению с PROTOCOL_STEPS.md: cmd 14 (дуга произвольного угла) есть в прошивке; yaw (6) = абсолютный курс `data[0]/10` градусов; atti (11) = крен и тангаж `data[0]/10`, `data[1]/10` (зажим ±10); speed (4) данных не читает; flip (8) в этой сборке отсутствует; jump (9) в миссии ничего не делает; local360 (7) данных (направления) не читает.
4. Время: `time` это абсолютный конец шага в 0,1 с. Следующий шаг начинается, когда выполнены оба условия: цель шага достигнута (все «done»-флаги) **и** до конца шага осталось не более 0,2 с. То есть время держит дрона в конце шага, а не гонит скорость.
5. Круг: `TIME` в блоке это время одного полуоборота (угловая скорость = 180 / T град/с), `COUNT` полуоборотов даёт `COUNT·180°`. Радиус = расстояние от **последней заданной цели** (а не от измеренной позиции) до центра.
6. ext-шаги (cmd 50 и 51, RGB) в этой сборке ядра полёта **ничего не исполняют** (в `mission_process_task` для них нет ветки), но срабатывают по абсолютному времени `time/10` с отдельным конвейером. Кто делает свет, в этом ELF не видно.
7. Загрузка миссии, её запуск (`status = 1`) и контрольная сумма в этом ELF вырезаны линкером (адрес 0 в DWARF). Поведение запуска выведено только по `mission_update`.

## 1. Структуры и состояние

`mission_node_s` (DWARF, 18 байт): `count` u16 (+0), `time` u16 (+2), `type` u8 (+4), `data` int16[6] (+6). **ПРОЧТЕНО.**
`mission_get_task_data(count, &time, &type, data)` (0x47c49764) берёт узел по адресу `missionData + (count-1)*18` и читает `+2` (time), `+4` (type), `+6..+17` (data). Поле `count` самого узла не читается; индекс шага определяется положением в массиве (нумерация с 1). **ПРОЧТЕНО.**
Ёмкость: символ `missionData` занимает 18432 байта, то есть 1024 узла (18432 / 18). **ВЫВОД** (по размеру символа).
Заголовок миссии `missionControl` (18 байт, 0x47c706cc): первое поле `u16` = общее число шагов (его сравнивают `mission_update_task` и `_ext`; функция `mission_get_task_total` отдаёт его в журнал). **ПРОЧТЕНО.**

Не найдено в ELF (DWARF-адрес 0, символа нет): `mission_add_task`, `setMissionCountTotal`, `mission_clear_task`, `mission_set_status_run`, `mission_set_time_sync`, `mission_set_checksum`, `mission_get_checksum`, `control_mission_set_move`, `control_mission_set_move_target`, `control_mission_update_move`, `control_mission_get_vel_done`, `bezier3`. Следствие: **НЕИЗВЕСТНО**, как именно в этой сборке миссия принимается, как считается контрольная сумма (в PROTOCOL_STEPS.md это сумма cmd) и как задаётся момент старта.

## 2. Режимы управления (`control_modes`, ПРОЧТЕНО)

`control_init` (0x47c3df6a) заполняет таблицу по 16 байт на режим: `check`, `init`, `exit`, `update`. `control_set_mode(mode, args)` (0x47c3de8c): проверяет `check`, вызывает `exit` старого, пишет новый режим, сбрасывает PID (`pid_pos_reset_param`, `pid_att_reset_param`), вызывает `init(args)` нового. Если у режима нет записи, пишется `mode:%d check null` и возвращается 0.

| № | Режим | Файл | Примечание |
|---|---|---|---|
| 0 | stabilize | app_control_stabilize | ручной |
| 1 | althold | app_control_althold | ручной |
| 2 | poshold | app_control_poshold.c | ручное удержание позиции |
| 3 | takeoff | app_control_takeoff.c | шаг takeOff |
| 4 | land | app_control_land.c | шаг autoLand |
| 5 | пусто | | в таблице нет |
| 6 | **mission** | app_control_mission.c | основной режим шагов движения |
| 7 | circle | app_control_circle.c | отдельный круговой режим для ручного управления (не из миссии) |
| 8, 9 | пусто | | записей нет (вероятно, вырезанный flip) |
| 10 | stop | app_control_stop | остановка, выключение моторов |
| 11 | local360 | app_control_local360.c | шаг local360 |
| 12 | jump | app_control_jump.c | «прыжок» (подробнее в разделе 6.6) |
| 13 | track_lines | app_control_track_lines.c | следование по линии (камера) |

Требования входа (`control_check`, 0x47c3db8e, маска): бит 0x1 attitude/IMU годны, 0x2/0x4/0x8/0x10 позиция (общая/abs/loc/rel) годна, 0x20/0x40/0x80/0x100 высота (общая/abs/loc/rel), 0x200 моторы взведены, 0x400 моторы не взведены. Для mission: 0x250 (взведён + высота abs + позиция rel) и ещё 0x8 (позиция loc), если включён `failsafe_enable` (0x47c40754). Для takeoff: 0x441 (attitude, высота abs, не взведён). Для land, jump, local360: 0x250. **ПРОЧТЕНО.**
`control_set_normal_mode` (0x47c3df1c): если миссия идёт (`mission_status == 1`), сбрасывает цели (`control_mission_set_target_init(0)`), входит в режим 6 и ставит `task_done`; если режим 6 не взялся, садится (режим 4). Если миссии нет: режим 2, при отказе режим 1. Это «возврат из takeoff, land, local360 обратно в миссию». **ПРОЧТЕНО.**
`control_set_stop_mode` (0x47c3df04): `mission_set_task_done()` и режим 10. **ПРОЧТЕНО.**

## 3. Планировщик миссии (`app_mission.c`)

### 3.1. Часы

`mission_update` (0x47c49e5c, вызывается из `main_loop`) каждый тик: **ПРОЧТЕНО**
* `mission_time_count` = секунды (float) с момента `mission_init` по часам `do_gettimeofday` (`get_diff_time`, 0x47c35210). `mission_time_start_count` = `mission_time_count - mission_time_sync_diff`.
* Если `mission_status == 1` и режим отказа не активен (`failsafe_get_mode() == 0`, иначе статус сбрасывается в 0 с сообщением `mission fs`), и `run_time_check == 0` и `mission_time_start_target < mission_time_start_count`, то включается `run_time_check`, начало часов шагов (`mission_task_time`) обнуляется (`get_diff_time(..., update=1)`), в журнал пишется `mission time start`. Это отложенный старт на заданный сетевой момент. **ПРОЧТЕНО**; кто задаёт `start_target`, **НЕИЗВЕСТНО** (`mission_set_status_run` вырезана).
* Далее `mission_task_time_count` = секунды с начала часов шагов. Если включена принудительная синхронизация (`time_force_enable`) и `|start_count - force_sync| < 0,1`, один раз вычисляется поправка `mission_time_force_sync_diff` и она вычитается из часов шагов. Детали синхронизации **ВЫВОД**.
* До `run_time_check` шаги не исполняются: `mission_update_task` и `mission_update_task_ext` вызываются только после него.
* Конец миссии: когда `ext_count >= total`, `task_count >= total`, `task_time_done` и `ext_time_done`, статус сбрасывается в 0 (сообщение `mission done`). Значит, последний шаг дожидается своего времени.
* Аварийный стоп: если `control_mission_get_failsafe_time() >= 0,1` с, то статус 0, режим 4 (посадка), сообщение об ошибке. `failsafe_time` растёт на `dt`, пока позиция loc невалидна (`control_mission_failsafe`, 0x47c41198), и сбрасывается в 0 при валидной позиции. Работает только при `failsafe_enable`, который каждый шаг движения включает в `mission_process_task`. **ПРОЧТЕНО.**

### 3.2. Выбор следующего шага (`mission_update_task`, 0x47c49cde)

Каждый тик: **ПРОЧТЕНО**
1. `task_time_error = task_time_target - task_time_count`.
2. Если `task_time_done == 0` и `task_time_error <= 0,2`, то `task_time_done = 1`. Если `task_time_done == 0` и ошибка больше 0,2, **функция возвращает управление**, новый шаг не берётся (адрес 0x47c49d30, переход на возврат).
3. Если `task_done == 0`, возврат.
4. Иначе перебор: `task_count` увеличивается, берётся узел; узлы с типом 50 и 51 пропускаются (проверка `(type-0x32) <= 1`); для первого подходящего: `task_done = 0`, `task_type = type`, `task_time_target = time / 10,0`; если `task_time_target > 0,01`, то `task_time_done = 0` и `task_time_error = target - count`; вызывается `mission_process_task(type, data, task_time_target)`; в журнал идёт строка `task c:%d ty:%d ti:%3.1f (data0..5)`. Цикл идёт до `task_count >= total`.

Итог для времени шага (**ПРОЧТЕНО**, формула **ВЫВОД**): шаг i+1 начинается в момент `max(момент достижения цели шага i, t_end(i) - 0,2 с)`. Если дрон долетел раньше, он ждёт; если позже, следующий шаг начинается сразу по завершении. `time` из кадра = **накопленное** время конца шага (с начала часов шагов), как в PROTOCOL_STEPS.md, делится на 10: единицы 0,1 с, поле u16 без знака (`fcvt.s.wu`).
Шаги с `time/10 <= 0,01` не сбрасывают `time_done` (ожидания нет).

### 3.3. ext-шаги (RGB и подобные)

`mission_update_task_ext` (0x47c49b86): **ПРОЧТЕНО**
* Хранит свой индекс `mission_task_ext_count`, свои `ext_type`, `ext_data[12 байт]`, `ext_time_target`, `ext_time_done`.
* Когда `ext_time_done == 1`, перебирает узлы дальше от своего индекса до `total`; берёт **только** узлы с типом 50 (0x32) или 51 (0x33); `ext_time_target = time / 10,0`, `ext_time_done = 0`.
* Затем ждёт, пока `mission_task_time_count >= ext_time_target`, ставит `ext_time_done = 1` и вызывает `mission_process_task(ext_type, ext_data, ext_time_target)`; в журнал идёт `ext c:%d:%d t:%3.1f (data0..5)`.
* Поэтому ext-шаги исполняются строго по порядку индексов, каждый по своему абсолютному времени на тех же часах, что и обычные шаги. Если в списке ext-шаг с более поздним временем стоит раньше по индексу, он задержит все следующие. **ВЫВОД** (прямое следствие последовательного перебора).
* Время ext-шага это **момент срабатывания**, а не длительность. Это согласуется с приложением (оно ставит им `часы - 3`, то есть 0,3 с раньше). Порядок «по месту» или «в конец» значения не имеет, только возрастание времени по индексу.
* **В `mission_process_task` для типов 50 и 51 ветки нет** (проверка границы `type > 0x14` ведёт на `ret`, 0x47c498a0). Значит, в этой сборке ядро полёта само ничего с RGB-данными не делает. Куда уходят данные света, **НЕИЗВЕСТНО**: функции `int_dev_rgb_ext_control`, `int_dev_rgb_control`, `notify_rgb_external_*` в ELF есть, но вызываются из `mklink_decode` (радиопульт) и `notify_task`, а не из миссии. Возможно, RGB обрабатывает другое ядро или другая прошивка (на Wing это `pilot`, где RGB проверено вживую).

| Поле | Источник |

## 4. Исполнитель режима 6 (`control_mission_update`, 0x47c41838)

Каждый тик (`dt`, `rc`): **ПРОЧТЕНО**
1. `control_mission_failsafe(dt)` (счётчик потери позиции, см. 3.1).
2. Высота: если `alt_vel_done` не выставлен, `update_alt_vel` (скоростной режим, ставится только ручным каналом), иначе `update_alt` (позиционный).
3. Курс: если `yaw_rate_done` не выставлен, `update_yaw_rate`; иначе если `yaw_rel_done` не выставлен, `update_yaw_rel`, иначе `update_yaw_abs`.
4. Горизонталь, приоритет сверху вниз: если `att_done == 0`, `update_att` (и больше ничего по горизонтали); иначе если `vel_done == 0`, `update_vel`; иначе если `circle_done == 0`, `update_circle`; иначе `update_pos`.
5. **Условие завершения шага**: если `mission_check_en` включён и **все** флаги `vel_done`, `pos_done`, `alt_done`, `alt_vel_done`, `yaw_rate_done`, `yaw_abs_done`, `yaw_rel_done`, `att_done`, `circle_done` равны 1, то `control_mission_set_target_init(0)` (все флаги в 1, `check_en` в 0) и при `mission_status == 1` `mission_set_task_done()`.
6. Если любая из четырёх осей стика пульта `rc[0..3]` не равна нулю, вызывается `control_set_normal_mode`: ручной ввод прерывает шаг (и завершает его, см. 2).

`control_mission_set_target_init(enable)` (0x47c4003a): `check_en = enable` и **все done-флаги = 1**; затем каждая `set_*_target` обнуляет только свой флаг. Поэтому шаг завершается, когда достигнуты все *заданные* им цели. `mission_process_task` вызывает `set_target_init(1)` только у шагов 3, 5, 6, 10, 11, 12, 13, 14.

Следствие (**ВЫВОД**, но из прочитанного условия): шаги, которые не вызывают `set_target_init(1)` и сами не завершаются через другой режим, не заканчиваются, потому что `check_en` после предыдущего шага равен 0. Это типы 4, 8, 9 и 15..19 (см. таблицу ниже). Миссия встанет на таком шаге до вмешательства стика (который вызовет `set_normal_mode`, то есть завершит шаг).

### 4.1. Поля журнала `log_CMISS_s` (0x47c48bac) и флаги

| Поле | Источник / смысл |
|---|---|
| `alt_sp_dist` | `mission_alt_sp_dist` = `|цель - текущая|` по высоте, м |
| `pos_sp_dist` | `mission_pos_sp_dist` = расстояние до цели в плоскости, м |
| `circle_deg_sp` | `mission_circle_deg_sp` = угол точки старта круга относительно центра (градусы 0..360) |
| `vel_limit`, `alt_vel_limit`, `yaw_limit` | текущие пределы скорости по XY (3,0 м/с макс.), по высоте (1,5), по курсу (0,5), см. ниже |
| `att_done`, `pos_done`, `alt_done`, `yaw_done`, `circle_done` | флаги завершения (`yaw_done` = `yaw_abs_done`) |
| `failsafe_time` | время без валидной loc-позиции, с |

`log_CMISS_C_s` (круг, 0x47c48d0e): `des`=`deg_sum` (накопленный угол, град), `ded`=`deg_diff` (остаток до 180°), `did`=`dist_diff`, `dicd`=`dist_centre_diff` (радиальная ошибка), `dep`=`deg_per` (доля угла), `tip`=`time_per` (доля оставшегося времени), `dtr`=`deg_time_ratio`, `vf`/`vff`=`vel_forward` и его фильтр, `va`/`vaf`=`vel_afferent` и фильтр, `vap`/`vai`=P и I радиального PID. `log_CMISS_P_s` (позиция, 0x47c48f1a): `did`=`pos_dist_diff` (боковая ошибка), `dicd`=`pos_dist_centre_diff` (продольная), `dip`=`dist_per`, `tip`=`time_per`, `dtr`=`dist_time_ratio`, `vf`=`vel_forward`, `va`=`vel_afferent`, `vap`/`vai` PID. Соответствие по порядку вызовов геттеров. **ПРОЧТЕНО**; физический смысл `vf` и `va` в управлении **ВЫВОД** (они в основном логируются, см. 6.4).

### 4.2. Пределы скорости и допуски (ПРОЧТЕНО)

* XY: `control_mission_pos_vel_limit` (0x47c3ff78) = `|pos_sp_dist / task_time_error|`, если ошибка времени больше 0, иначе 3,0. В `update_pos` ×1,1, зажим [0,5; 3,0] м/с, при NaN 1,75; передаётся в `control_pos_ned(dt, limit, 1,5, ...)`. Если цель уже достигнута (`pos_done`), предел затухает `×0,997 + 0,009`.
* Высота: `control_mission_alt_vel_limit` (0x47c3ffb2) = `|alt_sp_dist / task_time_error|` (иначе 1,5); в `update_alt` ×1,1, зажим [0,01; 1,5] м/с, при NaN 0,755.
* Курс: `control_mission_yaw_rate_limit` (0x47c3ffec) = `|цель - курс| / task_time_error` (иначе 0,5); в `update_yaw_abs` зажим [0,1; 0,5]; единица предела **НЕИЗВЕСТНО** (это «ограничение выхода PID курса» для `control_yaw_rate_common`, величина безразмерная). Практически почти всегда упирается в 0,5.
* Допуск `pos_done`: по каждой оси отдельно, защёлкой (раз попала в допуск, остаётся): `|ошибка| < max(0,2 м, 5 % начальной ошибки оси)`; когда обе оси попали, `pos_done = 1` (`update_pos`, 0x47c41742..0x47c41794).
* Допуск `alt_done`: `|цель - текущая| < max(0,03 м, 10 % начального отклонения)`.
* Допуск `yaw_abs_done`: `|wrap180(цель - курс)| < 5°` (0x47c40eb0).
* Все флаги и допуски ссылаются на `nav_get_pos_loc_ned_*` (локальная NED-позиция), цель берётся из `control_get_pos_loc_ned_target`.

### 5.1. Систему координат целей (moveXY, moveXYZ, центр круга)

* Цель позиции задаётся как `(x, y) = (data[0]/100, data[1]/100)` метров в «NED»-осях навигации. Первое поле это `x`, второе `y`. **ПРОЧТЕНО** (0x47c49ab4..0x47c49ae6, `control_mission_set_pos_target` берёт `pos[0]`, `pos[1]` как NED x и y).
* Выбор системы: если абсолютная позиция валидна (`nav_get_pos_abs_valid`), цель пишется в abs-цель; иначе loc; иначе rel (0x47c4043c..0x47c405ce). Управление идёт по loc-ошибке (`update_pos`). Как abs и loc связаны, **НЕИЗВЕСТНО** (функции `control_set_pos_abs_ned_target` и `control_set_pos_loc_ned_target` в этом разборе не раскрывались).
* Поправка к ковру: шаг миссии **сам ничего не прибавляет** (никаких «40 см на клетку» в `app_control_mission.c` нет), метры берутся как есть. Привязка к ковру живёт в `apriltag_get_id_pos` (0x47c36312): `y = (id % 12) · 40 · 0,01`, `x = (id / 12) · 40 · 0,01` (`rem` и `div` на 12, множитель 40, затем 0,01). То есть NED `x` это строка ковра, `y` это столбец, клетка 40 см. **ПРОЧТЕНО.** Это тот же порядок «сначала строка, потом столбец», что и в PROTOCOL_STEPS.md (проверено вживую для moveXY). Пересчёт клетки в сантиметры (`row_cm = 40·(клетка/12)`, `col_cm = 40·(клетка%12)`) делает приложение (`_transPos`), прошивка шагов этого не делает. Что `nav abs/loc` на реальном дроне совпадают с позицией по маркерам, **ВЫВОД**.
* Смещение стартовой клетки (откуда дрон взлетает): **НЕИЗВЕСТНО** (в разобранных функциях не обнаружено). Цель `loc` при взлёте берётся «как есть» (`control_set_pos_ned_target_curr`).

## 6. Подробно по шагам и режимам

### 6.1. takeOff (type 1, режим 3, `app_control_takeoff.c`)

* `control_takeoff_init(args)` (0x47c420e4): высота = `(u16 из байтов 0,1)·0,01` м; если значение не больше 0,0001 (то есть `data[0] == 0`), берётся 1,2 м (0x47c42144). Скорость подъёма `takeoff_vel_limit = 0,3` м/с. **ПРОЧТЕНО.** Единицы: сантиметры (как в PROTOCOL_STEPS.md). Тип u16, не знаковый (лежит собранным из двух `lbu`).
* `control_takeoff_update` (0x47c421c6): сначала раскрутка винтов (`motor_set_test`, `takeoff_spin_val` растёт от 0,1; через 2 с) → `nav_set_alt_abs_start`, `control_set_alt_dist(высота)`, включаются takeoff-режимы INAV и PID, курс обнуляется (`attitude_set_yaw(0)`, `pid_set_att_yaw_target(0)`: **курс «0» это направление при взлёте**). Затем подъём с удержанием позиции.
* Завершение: `|цель - высота| < 0,03 м` в течение более 1 с (`stableSumDt > 1`), либо стик тяги отклонён больше 0,3 → `takeoff_check_done`, затем `control_set_normal_mode` (возврат в режим 6 и `mission_set_task_done`). **ПРОЧТЕНО.**

### 6.2. autoLand (type 2, режим 4, `app_control_land.c`)

* `control_land_init` (0x47c3e2c2): `control_land_pos_loc_init`, PID высоты в режим посадки.
* `control_land_update` (0x47c3e4de): вертикальная скорость -0,5 м/с (если высота больше 0,3 м), иначе около -0,42 м/с (константы 0x47c58dd8 = -0,5 и 0x47c58ddc = -0,42), удержание позиции. Проверки касания (`land_check`, `check_acc` с порогом -15 по ускорению, `check_thr`). По касанию `control_set_stop_mode`: `mission_set_task_done()` и режим 10 (stop). **ПРОЧТЕНО** (структура), конкретные пороги **ВЫВОД**.
* Данные шага не читаются. Время шага влияет только на момент начала следующего шага, но после посадки дрон в режиме stop.

### 6.3. moveXY, moveZ, moveXYZ, yaw (режим 6)

* **moveXY** (3): `set_target_init(1)`, `failsafe_enable(1)`, `control_mission_set_pos_target({x, y})`. Если новая цель равна текущей `control_get_pos_abs_ned_target` по обеим осям, функция выходит и `pos_done` не сбрасывается (шаг завершится сразу, «ничего не делать»). Иначе: считаются `mission_pos_rad` (азимут `atan2`), `pos_time_all = task_time_error`, `pos_dist_all`, `pos_vel_avg = dist/time` (для журнала), цель записывается, PID сбрасывается, `pos_done = 0` (0x47c4043c). Движение: `update_pos` (4.2). **ПРОЧТЕНО.**
* **moveZ** (5): `control_mission_set_alt_target(d0/100)` (0x47c4067c). NaN становится 4,1 м; значение меньше 0,2 м становится 0,2; больше 8 м становится 8 (зажим [0,2; 8] м). Если новая цель отличается от текущей `control_get_alt_dist_target` больше чем на 0,001, вызывается `control_set_alt_dist` (цель высоты над землёй) и `alt_done = 0`. **ПРОЧТЕНО.** Высота **абсолютная над землёй** (метр = `dist`, а не прибавка).
* **moveXYZ** (10): то же, что moveXY плюс moveZ: обе цели ставятся в одном шаге (0x47c49a6e), порядок вызовов: сначала позиция, затем высота. Раскладка совпадает с PROTOCOL_STEPS.md (`row`, `col`, `z`), `data[3..5]` не читаются. Z абсолютная. Интерполяция «по прямой» не гарантирована: XY и Z регулируются независимо своими контурами, скорость XY ограничена `dist/time_error` (см. 4.2). **ПРОЧТЕНО / ВЫВОД**.
* **yaw** (6): `control_mission_set_yaw_abs_target(d0/10)` градусов; `update_yaw_abs` (0x47c40e34) держит курс через `control_yaw_common`; завершение при отклонении менее 5°. «Абсолютный» курс отсчитывается от нуля, который выставила последняя инициализация курса (`takeoff`: `attitude_set_yaw(0)`), а `locator_yaw_correct` может подправлять цель по маркеру. **ПРОЧТЕНО / ВЫВОД** (опорное направление не проверялось).

### 6.4. circle, circleAlt, cmd 14 (круг вокруг центра)

`control_mission_set_circle_target(центр[2], время, ccw, count)` (0x47c4008e) и `control_mission_set_circle_angle_target(центр[2], время, ccw, угол)` (0x47c40260): **ПРОЧТЕНО**
* Центр = `(data[0]/100, data[1]/100)` м, те же оси, что у moveXY (x = строка, y = столбец).
* `радиус = hypot(цель_x - центр_x, цель_y - центр_y)`, где `цель` это **последняя заданная цель** из `control_get_pos_loc_ned_target` (не измеренная позиция дрона). Радиус сохраняется как `mission_circle_radius`.
* Угол отсчёта: `θ = atan2(Δx, Δy)` (Δx вдоль первой оси «строка», Δy вдоль второй «столбец»), в градусах. `mission_circle_deg_sp` = θ точки цели (старт дуги), `deg_old` = θ измеренной позиции.
* Время: для circle и circleAlt `deg_rate = 180 / время` град/с (0x47c401c4), `deg_count_sp = count · 180`. **Время это один полуоборот.** Для circleAlt `count = 1,0` зашит (0x47c499da). Для cmd 14 `deg_rate = угол / время`, `deg_count_sp = угол`, то есть время это **вся дуга**.
* Время берётся как `data[2]/10` с (`int16`, знаковое).
* Число полуоборотов `data[3]` (`int16`, знаковое, то есть 2 байта, не 1), для circleAlt вместо него идёт высота.
* Направление: `ccw = (data[4] != 0)` (`int16` из байтов 8,9). Ненулевое значение это против часовой. В PROTOCOL_STEPS.md: 0 = cw, 1 = ccw: совпадает.
* Выставляются: `deg_count = 0`, `circle_end = 0`, `circle_done = 0`, `vel_avg = π·радиус/время` (для журнала), `time_all = task_time_error`.

Движение (`control_mission_update_circle`, 0x47c40dc6; `mode1` 0x47c408ec): **ПРОЧТЕНО**
* Каждый тик: шаг угла `δ = dt · deg_rate`; при `ccw`: `deg_sp += δ`, `deg_count += δ`; иначе `deg_sp -= δ`, `deg_count -= δ`.
* Цель позиции: `x = центр_x + радиус·sin(deg_sp)`, `y = центр_y + радиус·cos(deg_sp)` (в радианах; `deg_sp` растёт при `ccw`). Цель записывается `control_set_pos_loc_ned_target`; регулятор `control_pos_ned(dt, 3,5, 1,2, ...)`.
* Конец: когда `|deg_count| >= deg_count_sp`, ставится `circle_end`, после чего `circle_done = 1` на ближайшем тике. Скорость вращения цели фиксированная и от времени шага не зависит (подгоняющий режим `mode2` вычисляется, но результат `mission_circle_vel_ned` нигде не читается: перекрёстные ссылки дают только запись, **ПРОЧТЕНО**).
* Следствие по длительности: шаг circle занимает около `count · T` секунд (при `T = data[2]/10`), но следующий шаг не начнётся раньше `t_end - 0,2 с`. Значения `t_end` (накопленное) и `T·count` приложение держит согласованными. Если `t_end` позже, дрон ждёт; если раньше, шаг всё равно длится `count · T` и сдвигает остальное. Радиус дрона при этом не меняется.
* Высота при circle (12) не меняется (цель высоты не ставится); в circleAlt (13) и cmd 14 `set_alt_target(data[3]/100)` с теми же зажимом [0,2; 8] м и абсолютным смыслом.
* Знак вращения: при `ccw = 0` угол `deg_sp` убывает, то есть вращение по часовой при взгляде, где первая ось (x, строка) направлена «вверх», вторая (y, столбец) «вправо» (математический угол `atan2(x, y)`). Направление на реальном ковре зависит от того, как ось строк нарисована относительно дрона, поэтому **ВЫВОД**. Проверка по схеме: старт `(80, 80)`, центр `(80, 120)`, `ccw = 0`: θ0 = 180°, убывает до 90°, цель проходит через `(120, 120)`, то есть дуга выгибается в сторону больших строк, что совпадает с ожиданием из теста C1 в PROTOCOL_STEPS.md (раздел 11.3).

### 6.5. local360 (type 7, режим 11, `app_control_local360.c`)

* `process_task` вызывает `set_mode(11, 0)` без данных, поэтому `data[0]` (направление в PROTOCOL_STEPS.md) **не читается**. **ПРОЧТЕНО** (0x47c49b70).
* `control_local360_init` (0x47c3fc0a): `init_yaw` = текущий курс, `l_status = 0`.
* `control_local360_update` (0x47c3fc62): с удержанием позиции (`control_pos_ned(dt, 0,5, ...)`, если позиция валидна, иначе `control_att_common_rc`) и стиком высоты (`control_alt_rc`) подаётся постоянный сигнал скорости рыскания `control_yaw_rate_common(dt, 0,3, 1,0)` в **одну и ту же сторону** (знак положительный).
* Статусы: 0 → 1 когда курс ушёл от начального более чем на 90°; 1 → 3 когда `|курс - init_yaw| < 1,0` (вернулся); 3 → `control_set_normal_mode` (конец шага). Итог: **один оборот на 360° вокруг вертикальной оси на месте**. Время оборота определяется скоростью, а не `time` шага. Стик (`rc[0]` или `rc[1]` ≠ 0) прерывает. **ПРОЧТЕНО.**
* Единицы «0,3» (безразмерный выход, зажим [-1,0; 1,0]) и физическое направление (по часовой или против) **НЕИЗВЕСТНО**.

### 6.6. jump (режим 12, `app_control_jump.c`) и flip

* **Из миссии не вызываются**: type 9 это пустая ветка (0x47c498c0). Режим 12 можно включить только через `control_set_mode` из других мест (`mklink_decode` вызывает с режимом из пакета; подробности **НЕИЗВЕСТНО**).
* Сам режим (**ПРОЧТЕНО**): `control_jump_init` (0x47c3facc) запоминает `alt_abs_min = текущая высота`, `alt_abs_max = текущая + 0,35 м`, `jump_up = 1`. `control_jump_update` (0x47c3fb38): пока `jump_up`, скорость высоты +0,2 м/с до `alt_abs_max`, затем -0,2 м/с до возврата на `alt_abs_min`; в плоскости удержание позиции (`control_pos_ned`, 0,7). Это «подпрыгивание» на 35 см. После возврата `jump_up` снова ставится в 1 (так и работает циклически; выхода из режима нет, кроме смены режима).
* **flip** (type 8) в этой сборке отсутствует: режимы 8 и 9 пусты, отдельного файла `app_control_flip.c` в DWARF нет, но структура журнала `log_FLIP_s` (roll, pitch, yaw, mode, stable_roll, stable_pitch) и функции `inav_*_set_flip_mode`, `ahrs_set_flip_mode` в символах есть. Значит, переворот существовал в другой сборке; что он читал из `data`, **НЕИЗВЕСТНО**.

### 6.7. atti (type 11) и speed (type 4)

* **atti**: `set_target_init(1)`; `control_mission_set_att_target({d0/10, d1/10})` (0x47c406ee) записывает цель и обнуляет `att_done`. `update_att` (0x47c408d0) вызывает `control_att_common(dt, roll = att_sp[0], pitch = att_sp[1], rate_limit = 0,5)`. В `control_att_common` (0x47c3ee50) оба угла зажимаются в [-10; 10] (единицы вероятно градусы: `data` в 0,1° → максимум 100). NaN становится 0. **ПРОЧТЕНО.** Единица «градус» и знаки крена/тангажа **ВЫВОД**/**НЕИЗВЕСТНО**.
  Флаг `att_done` пишут только `set_att_target` (в 0) и `set_target_init` (в 1); обновление его не выставляет. Поэтому шаг atti сам не заканчивается, горизонтальная часть режима 6 всё время занята `update_att` (приоритет над vel, circle, pos). Закончить может только стик (ввод `rc` → `set_normal_mode`). **ВЫВОД** из прочитанного.
* **speed** (4): ветка 0x47c4993e только входит в режим 6, цели не меняются и данные не читаются. Скоростной интерфейс (`control_mission_set_vel_target`, `..._alt_vel_target`, `..._yaw_rate_target`) вызывается только из `mklink_decode` (радиопульт). Шагом миссии скорость задать нельзя. **ПРОЧТЕНО** (отсутствие вызовов в `mission_process_task`).

### 6.8. Прочие режимы (кратко)

* **poshold** (режим 2): ручное удержание позиции со стейт-машиной «движение / торможение 1 / торможение 2» (`control_poshold_*_status`); в `init` берёт позицию маркера (`apriltag_get_id_pos`) и ставит loc-цель. Для миссии не используется. **ПРОЧТЕНО** (структура), детали торможения не разбирались.
* **circle** (режим 7, `app_control_circle.c`): отдельный круговой режим ручного управления: статусы START/ON/END/STOP/OFF, тело в `control_circle_vel_on` (крен ограничен около -0,21 рад ≈ -12° и 30° по константам), управляет скоростью по телу и рысканием. Из миссии не вызывается. Назначение как «орбита с наклоном» **ВЫВОД**, детали не разбирались.
* **track_lines** (режим 13): следование по линии по данным камеры (`cameraData_s`); есть сеттеры `control_track_lines_set_speed`, `_set_alt`, `_set_yaw`. Не связан с шагами миссии. Детали не разбирались.
* **common_pos** (`app_control_common_pos.c`): набор общих контуров: `control_alt` в режимах abs/loc/rel и `dist` (высота над землёй), `control_pos_ned` (abs/loc/rel NED), `control_vel_ned`, `control_vel_grd`; при потере валидности системы позиции переключается на следующую (abs → loc → rel). **ПРОЧТЕНО** (структура), численные параметры контуров не разбирались.

## 7. Отказобезопасность, влияющая на миссию (`app_failsafe.c`)

* `failsafe_update` (0x47c4376c) вызывает проверки: потеря радио (`rc_lost_check` → режим 4), низкая батарея (`low_batt_check` → режим 4), перегрев (`high_temp_check` → режим 4), превышение угла (`att_limit_check` → режим 10), столкновение (`collision_check` → режим 10), а также `power_down_check`, `motor_locked_check`. Режимы по константам `set_mode` рядом с проверками (адреса 0x47c43438, 0x47c434ca, 0x47c43544, 0x47c435b4, 0x47c436cc). **ПРОЧТЕНО.**
* `failsafe_get_mode() != 0` останавливает миссию (`mission_status = 0`, см. 3.1). После этого подхватывает посадка или стоп, которые выбрал сам failsafe. **ПРОЧТЕНО.**
* Режимы 4 (land), 9 и 10 (stop) исключены из проверки низкой батареи при смене режима (`control_set_mode`, 0x47c3deac); для остальных при низкой батарее `set_mode` отказывает (`set mode:%d failed,low power`). **ПРОЧТЕНО.**
* Дополнительно в миссии: потеря loc-позиции на 0,1 с и более ведёт к посадке (3.1). **ПРОЧТЕНО.**

## 8. Сверка с PROTOCOL_STEPS.md и расхождения

| Утверждение в PROTOCOL_STEPS.md | Что в прошивке | Оценка |
|---|---|---|
| Кадр `[... total, index, t_lo, t_hi, cmd, 12 байт]`, `t` накопленное, тики 0,1 с | `time` u16 /10 = конец шага; `type` u8; `data[6]` int16 (подтверждено структурой `mission_node_s` и `mission_update_task`) | совпадает (**ПРОЧТЕНО**) |
| moveXY (3): `i16 row, i16 col`, 8 нулей | `data[0]/100`, `data[1]/100` как NED x, y | совпадает |
| moveZ (5): `u16 z_cm` | читается как **знаковое** `int16`, `/100`, зажим [0,2; 8] м (то есть 20..800 см); значения меньше 20 см превращаются в 20 см | уточнение |
| moveXYZ (10): `i16 row, col, z`, Z абсолютная | `data[0..2]/100`; Z абсолютная над землёй (`dist`); `data[3..5]` не читаются | совпадает; потолок высоты в прошивке 8 м, а не 2 м (потолок 2 м в проекте это проектное ограничение) |
| «Высота остаётся внутри лимита проекта» | в прошивке жёсткого лимита 2 м нет, только зажим 0,2..8 м | расхождение уровня (не ошибка) |
| circle (12): `[i16 row, i16 col, u16 T, count, 0, dir, 0,0,0]` | `data[2]` = T (`int16`), `data[3]` = count (**int16**, 2 байта, а не 1), `data[4]` = dir (**int16**, ненулевое = ccw) | совпадает, но `count` и `dir` двухбайтовые |
| Раздел 12/8: `count` ≤ 255 (один байт) | прошивка читает `int16` | уточнение (до 32767, отрицательные бессмысленны) |
| Время шага circle = `T·count`, `TIME` на один полуоборот | подтверждено: `deg_rate = 180/T`, путь `count·180°` | **совпадает** (**ПРОЧТЕНО**) |
| Радиус = расстояние от **текущей позиции дрона** в начале шага до центра | радиус = расстояние от **последней заданной цели** до центра (`control_get_pos_loc_ned_target`); начальный угол тоже от цели | **расхождение**; ошибка позиции дрона (раздел 12, п. 3) на радиус не влияет, зато цель должна быть корректной (шаг перед кругом обязан поставить цель на нужное расстояние) |
| Угол = ±180° × count, знак по dir, равномерно | `dt · 180/T` за тик, `ccw` = ненулевое | совпадает |
| Высота при circle не меняется | цель высоты не ставится в type 12 | совпадает |
| Использует ли прошивка T или считает по `t_end` (вопрос 2) | использует `T` (`data[2]`); `t_end` в расчёте скорости круга не участвует. `t_end` лишь влияет на момент старта следующего шага | **ответ получен** |
| circleAlt (13): центр, T, i16 z (байты 6-7), dir (байт 8), один полуоборот, Z абсолютная | `data[2]` = T, `data[3]` = z (`/100`), `data[4]` = dir, `count = 1,0` зашит, Z абсолютная (зажим 0,2..8 м) | совпадает |
| cmd 14 (AroundD): «как 13 + i16 degree в байтах **9-10**», «в прошивке неизвестно» | **есть**: `data[5]` = **u16 угол в градусах, байты 10-11**; `data[4]` (байты 8-9) = направление; время `data[2]` это время **всей дуги** | **расхождение** по смещению (байты 10-11, не 9-10) и по статусу (прошивка его поддерживает); время иное, чем у 12 и 13 |
| local360 (7): `[0] dir` | данные не читаются; направление фиксировано; один оборот возвращает курс в начальный (±1°) | **расхождение**: байт направления игнорируется (задавать смысла нет) |
| speed (4), yaw (6), flip (8), jump (9), atti (11): «раскладка неизвестна» | speed: данных нет, ничего не делает кроме входа в режим 6; yaw: `data[0]/10` град, абсолютный курс; flip: режима нет; jump: пусто; atti: `data[0]/10` и `data[1]/10` (зажим ±10) | **закрыты вопросы**; шаги 4, 8, 9, 11 в миссии опасны (не завершаются, **ВЫВОД**) |
| RGB (50): время `часы-3`, ext-шаги идут отдельным списком в конец | ext-конвейер подтверждён: ext-шаги берутся из того же массива по индексу, но запускаются по абсолютному времени на общих часах, независимо от места среди шагов движения. Нужна монотонность времени по индексу. Саму обработку (раскладка `[5,0,2,255,g,r,b]`) в этом ELF `process_task` не выполняет | подтверждено частично; **НЕИЗВЕСТНО**, кто исполняет RGB |
| «Контрольная сумма дрона = сумма cmd всех шагов» | функции `mission_set_checksum` и `get_checksum` вырезаны | **НЕИЗВЕСТНО** |
| Позиция клетки `[40·(cell/12), 40·(cell%12)]`, row первым | прошивка принимает метры по осям NED (x = строка); поправки в миссии нет; `apriltag_get_id_pos` использует тот же порядок | совпадает (**ПРОЧТЕНО**) |
| Симулятор: moveXYZ по прямой равномерно | прошивка регулирует XY и Z независимо, скорость XY из `dist/time_error` не ниже 0,5 м/с, поэтому траектория не равномерна по времени. К точке в конце шага дрон приходит не позже `t_end - 0,2 с` только если его хватает по скорости (максимум 3 м/с по XY, 1,5 по Z) | **расхождение с симулятором** (**ВЫВОД**) |

Что **подтвердилось** одной строкой: структура кадра, порядок «row, col», время в 0,1 с (накопленное), единицы сантиметры для приложения, `T` на полуоборот, радиус круга ненулевой, число полуоборотов в байте 6, направление в байте 8, высота в байтах 6-7 у circleAlt.

## 9. Рекомендации для проекта (по прочитанному)

1. `Drone.circle(count, seconds, ...)` в `show.py`: прошивка считает `seconds` как время **полуоборота**. Не менять модель вслед за предположением «общее время»; шаг по прошивке длится `count·T`.
2. Перед `circle` обязательно ставить цель на нужный радиус (например `code` на клетку) и ждать её достижения: радиус берётся от последней **цели**, не от измеренной позиции. Если цель совпадает с центром, радиус 0 и круга не будет.
3. Времена шагов делать **возрастающими**; избегать типов 4, 8, 9, 11, 15..19 в загружаемых программах (шаг не заканчивается, миссия встанет до вмешательства стика).
4. Для `local360` направление не задаётся; данные можно слать нулями.
5. Если нужна дуга произвольного угла, использовать cmd 14: байты `[0-1] row, [2-3] col, [4-5] T_дуги (0,1 с), [6-7] z_cm, [8-9] dir, [10-11] угол (градусы)`. Проверять вживую по одному дрону: поведение выведено только по коду.
6. Все эти выводы относятся к `melis30_1.5.elf` («тестовая 1.5», RISC-V). Живая проверка PROTOCOL_STEPS.md велась на Wing (A33, `pilot`), код которого родственный, но не тот же. Совпадение логики шагов нужно подтверждать на устройстве.

## 10. Как это читалось (чтобы повторить)

* Адреса функций из DWARF (`dwarf_types.py <файл.c>`) и таблицы `.symtab` (статические переменные и функции тоже есть: `mission_*`, `control_mission_*`).
* Дизассемблирование: `tools/firmware/riscv_disasm.py`. Для чтения потребовалась доработка вне репозитория (скрипты были в scratchpad): разбор длины команды по двум младшим битам (команды T-Head `0x0b` длиной 4 байта, иначе поток расходится), абсолютные адреса переходов (`jal`), привязка `auipc`+`addi`/`lw` к символам.
* Таблица переходов `mission_process_task`: адрес базы 0x47c5a85c, 21 слово, значение это смещение (знаковое) от адреса базы. Подтверждена согласованностью с номерами режимов `set_mode`.
* Перекрёстные ссылки (кто читает или пишет переменную) получены сканированием всего `.dram_seg.text` по парам `auipc`+`addi`/`lw`/`sw`; результаты по функциям проверялись чтением тела.
* Не разбирались: подробности `control_pos_ned` и PID, `pid_set_pos_mission_*_mode*`, `yawAngleTrim`, `app_control_poshold` целиком, `app_control_circle` целиком, `track_lines` целиком, `control_mission_update_vel`, `control_mission_update_alt_vel`, `update_yaw_rate`, `update_yaw_rel` (они управляются только радиопультом).
